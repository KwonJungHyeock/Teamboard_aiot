# MD-P-2026-032 — 마이그레이션 러너 조사 (`0031` 이 왜 이력에 없는가)

관찰: 프로덕션 `schema_migrations` 에 `0029` · `0030` 은 있고 **`0031` 이 없다.**
0029 → 0030 은 **47ms 간격**. 거기서 멈췄다.

PM 지시대로 네 가지를 밝혔다. **밝히지 못한 것도 그대로 적는다.**

---

## ① 파일이 배포에 들어갔는가 — **들어갔다**

```
$ git show 773d683:db/migrations/ | grep 0031
0031_orphan_tasks_to_standing.sql
```

`main` 과 `origin/main` 둘 다에 있다. **원인은 커밋이 아니다.**

### 그리고 「0029·0030 만 있는 트리」는 배포된 적이 없다

처음에 세운 가설은 이랬다 — 47ms 는 러너 한 번의 통과이므로,
**0029 와 0030 만 들어 있는 트리**에서 돌았을 것이다. 그런 트리는 배치 ② 커밋
(`fad7760`) 하나뿐이고, 브랜치 미리보기 배포가 프로덕션 DB 를 물고 있었다면
정확히 이 모양이 된다.

**그 가설은 틀렸다.** reflog 가 밝혔다.

```
$ git reflog show origin/claude/md032-a --date=iso
5b501f6 @{2026-08-27 07:40:04}: update by push
4b6747d @{2026-08-27 07:23:35}: update by push
```

브랜치는 **두 번만** 푸시됐다. 배치 ①②③은 로컬에서 세 커밋으로 나뉘었지만
**한 번에 함께 올라갔다.** 그러므로 배포된 트리는 셋뿐이다.

| 배포 | 커밋 | 시각(UTC) | 그 트리의 `db/migrations` |
| --- | --- | --- | --- |
| 미리보기 | `4b6747d` | 07:23:35 | 0028 까지 (새 것 없음) |
| 미리보기 | `5b501f6` | 07:40:04 | **0029 · 0030 · 0031 전부** |
| 프로덕션 | `773d683` | 07:56:37 | **0029 · 0030 · 0031 전부** |

**0029·0030 을 가진 배포는 전부 0031 도 가지고 있었다.**
「파일이 아직 없어서 안 돌았다」는 성립하지 않는다.

---

## ② 러너가 실패를 어떻게 다루는가 — **삼키지 않는다**

`lib/migrate.ts` 는 파일마다 자체 트랜잭션을 열고, 실패하면
`ROLLBACK` → `console.error` → `throw` 한다. `lib/db.ts` 의 `ensureMigrated()` 도
`migratePromise = null` 로 캐시를 비운 뒤 **되던진다.** 빈 `catch` 가 없다.

읽어서 그렇게 보인다는 것으로는 부족해서 **실제로 실패시켜 봤다.**

`scripts/migrate-runner-walk.mjs` — 진짜 `lib/migrate.ts` 를 tsc 로 컴파일해
임시 디렉터리에서 돌린다(러너를 .mjs 로 다시 쓰면 다시 쓴 것이 맞다는 증거밖에
안 된다). 가짜 마이그레이션 `9001 정상` · `9002 문법오류` · `9003 정상` 을 넣었다.

```
OK   ① 실패한 파일이 있으면 예외를 올린다 — “마이그레이션 실패 (9002_walk_boom.sql): syntax error at or near "THIS"”
OK   ① 예외 메시지가 **어느 파일**인지 말한다
OK   ② 실패 앞의 파일만 이력에 남는다 — 이력 [9001_walk_a.sql]
OK   ② 실패 뒤 파일은 **실행조차 되지 않는다** (표가 안 생겼다)
OK   ③ 고친 뒤 남은 것만 적용한다 — applied [9002, 9003] · 이미 32
OK   ④ 파일은 있는데 이력에 없는 것을 짚어낸다
OK   ④ 물어보기만 했을 뿐 **적용되지 않았다**
10/10 통과
뒷정리 확인 — 9xxx 이력 0 · tb_walk_* 표 0
```

②의 두 번째 줄이 핵심이다. 「이력에 없다」만 보면 부족하다 —
**9003 이 돌았는데 이력만 안 남았을 수도** 있기 때문에, 표가 생겼는지를 본다.
안 생겼다. 러너는 실패 지점에서 정말로 멈춘다.

> **결론 — 러너가 실패를 조용히 넘기고 있지는 않다.**
> 만약 0031 이 실패했다면 그 요청은 500 이 났어야 한다.

## ③ 오류가 어디에 남았는가 — **못 본다**

**Vercel 런타임 로그를 우리는 볼 수 없다.** 프로덕션 이그레스 허용 목록에
`teamboard-aiot.vercel.app` 이 없고, 자격증명도 없다. 그러므로
「그 시각에 500 이 났는가」를 **확인할 방법이 없다.**

추측으로 메우지 않는다. **못 본다를 적는다.**

그리고 **이것이 이번 조사에서 가장 아픈 지점이다.** 러너는 예외를 올리는데,
그 예외가 닿는 곳이 우리가 못 보는 로그 하나뿐이라면 **올리는 것과 삼키는 것의
차이가 밖에서는 없다.** 아래 수정은 그 차이를 DB 에 남기는 일이다.

## 남은 것 — **원인을 못 정했다**

세 가지를 지웠다. 파일 없음(①) · 러너가 삼킴(②) · SQL 자체(④).
남는 것은 **0030 커밋 직후와 0031 시작 사이에서 끊겼다**는 것뿐이고,
그 끊김이 둘 중 어느 쪽인지는 **여기서 가릴 수 없다.**

| | 그러면 어떻게 되는가 | 왜 못 가리는가 |
| --- | --- | --- |
| **(가)** 0031 이 실패했다 (연결 끊김 등) | 예외 → 그 요청 500 | 로그를 못 본다(③) |
| **(나)** 0031 에 **도달하지 못했다** (프로세스/요청 종료) | 예외가 **아무 데도 안 남는다** — 받을 사람이 이미 없다 | 흔적 자체가 없다 |

**(나)가 더 유력하다** — 마이그레이션은 사용자 요청 안에서 돌고, 서버리스 함수는
응답이 끝나면 언제든 얼어붙거나 회수된다. 다만 **유력한 가설일 뿐 확정이 아니다.**

그리고 어느 쪽이든 **한 가지는 확실하다.**

> 다음 요청이 재시도한다. 그러나 **그 사이에 아무도 모른다.**

0031 은 다음 프로덕션 DB 접근에서 적용된다(혹은 이미 됐다).
사이트는 그동안 정상으로 떠 있었고 오류도 안 났다. PM 이 `schema_migrations` 를
직접 조회하지 않았으면 **영영 몰랐을 것이다.** 그것이 이번의 진짜 결함이다.

## 무엇을 고쳤는가

### 1. 「어느 배포가 적용했는가」를 DB 에 남긴다

`schema_migrations.applied_by` — `production:main@773d683` 같은 값.
러너 자신의 표라서 마이그레이션 번호를 쓰지 않고 부트스트랩에서
`ADD COLUMN IF NOT EXISTS` 로 만든다. 새 DB 든 이미 돌던 DB 든 같은 한 줄로 맞는다.

이걸로 이번 같은 일이 다시 나면 **DB 만 보고** 미리보기인지 프로덕션인지 가린다.
Vercel 로그가 없어도 된다.

### 2. 「무엇을 할 작정인가」를 **하기 전에** 적는다

```
[migrate] production:main@773d683 · 파일 32 · 이력 30 · 적용 예정 2건: 0031_….sql, 0032_….sql
```

중간에 프로세스가 내려가도 이 줄은 남는다. **(나)의 유일한 흔적**이 된다.
실패 시 로그에도 「뒤따르던 N건은 적용하지 않는다」를 함께 적는다 —
「하나 실패」와 「하나 실패 + 다섯 대기」는 급한 정도가 다르다.

### 3. **러너를 돌리지 않고** 밖에서 물을 수 있게 한다

`migrationStatus()` / `lib/db.ts` 의 `getMigrationStatus()` / `GET /api/admin/migrations` (팀장 전용).

```json
{ "ok": false, "lastFile": "0032_….sql", "lastApplied": "0030_….sql",
  "counts": { "files": 32, "applied": 30, "missing": 2 },
  "missing": ["0031_….sql", "0032_….sql"], "unknown": [], "applied": [ … ] }
```

**일부러 `ensureMigrated()` 를 부르지 않는다.** 「어디까지 적용됐는가」를 묻는 일이
그 자체로 적용을 일으키면, 물어본 **뒤**의 답만 볼 수 있고 **묻기 전의 상태**를
영영 못 본다. 0031 을 알아챘을 때 필요했던 것이 바로 그 「묻기 전」이다.
검사기가 이것을 확인한다(④ — 물어본 뒤에도 표가 안 생겼다).

`unknown` 은 짝이 되는 단언이다 — 이력에는 있는데 파일이 없는 것.
파일을 지웠거나 되돌린 뒤 이력을 안 지운 경우가 보인다.

### 4. `MIGRATIONS_DIR` 을 한 곳에서만 계산한다

목록을 세는 쪽과 파일을 읽는 쪽이 경로를 따로 계산하고 있었다.
「목록에는 있는데 못 읽는」 상태가 생길 수 있는 모양이라 상수 하나로 합쳤다.

## 검사기 자신이 틀릴 뻔한 곳 (§G 재료)

**⑥ 「이력에만 있고 파일이 없는 것」이 옳은 답을 틀린 이유로 냈다.**
검사기는 임시 cwd 에서 도는데 거기엔 진짜 `db/migrations` 가 없다. 그래서
`unknown` 에 **0001~0031 이 전부** 잡힌다. `unknown.includes(F1)` 만 보면 참이지만,
**F1 을 지워서 참인지 원래 다 그런지 구분이 안 된다.** 9xxx 로 좁혀서 다시 세었다.

> 부재를 단언할 때는 **그 부재가 내가 만든 조건 때문인지** 먼저 확인한다.
> 통과하는 단언일수록 그렇다.
