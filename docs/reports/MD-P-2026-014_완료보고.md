## 1. 작업 요약 (3줄)

1. 업로드를 `put(pathname, file, { access: 'private' })` 로 바꾸고, DB에는 공개 URL이 아니라 **pathname·원본 파일명·크기·contentType** 을 저장한다.
2. 인증·인가를 **라우트 핸들러 안에서 직접** 하는 스트리밍 경로 `GET /api/blob` 을 만들고, 화면의 모든 이미지가 이 경로만 쓰게 했다.
3. 공개 URL을 만들던 구 업로드 라우트를 폐쇄(410)했고, 블록이 사라지면 blob 객체도 지운다.

`tsc --noEmit` 0오류 · `npm run build` 성공 · 전 16화면 200 / 콘솔·5xx 오류 0.

## 3. [기준과 다르게]

### ① 구 공개 업로드 라우트를 삭제하지 않고 **410** 으로 폐쇄했다

`/api/review/upload` 는 `access: 'public'` 으로 blob 을 만들던 경로다. Private 스토어에서
이 경로를 남겨두면 URL 유출 = 열람이 된다. 라우트 파일을 지우면 호출자가 404 만 보고 원인을 못 찾으므로,
**410 Gone + 대체 경로 안내**로 바꿨다. 기능이 아니라 위험 경로를 닫은 것이다.

### ② 시그널 **생성 시점**의 파일 첨부는 넣지 않았다 — 회신 ③에서 **현행 유지 확정**

경로 규칙이 `signals/{id}/…` 인데 생성 시점에는 id 가 없어 경로를 검증할 수 없다.
검증 없이 받으면 남의 시그널 경로를 심을 수 있다. 그래서 생성 폼은 기존대로 URL 입력만 두고,
**파일 첨부는 생성 후 코멘트로** 올리게 했다. (허들 메모 폼의 "이미지 URL" 입력은 그대로 유지)

### ③ 권한 없음에 403이 아니라 **404**

지시서 §B 그대로다. 다만 이 때문에 "권한 없음"과 "스토리지 오류"가 응답으로 구분되지 않는다.
의도한 트레이드오프이며, 사용자에게는 §C 의 실패 안내로 설명한다.

### 4-5. Preview 배포에서 확인할 항목 (회신 ② — 팀장 수행)

이 개발 환경에는 실제 blob 자격 증명이 없고, 아웃바운드 프록시가 `blob.vercel-storage.com` 을 차단한다.
아래 5건은 **실제 blob 객체가 있어야만** 판정되므로 Preview 배포에서 확인한다.
대상: 브랜치 `claude/new-session-58fqtb` 의 Preview URL.

| # | 항목 | 절차 | 통과 기준 |
| --- | --- | --- | --- |
| 1 | 업로드·표시 | 프로젝트 → `캔버스` 탭 → `＋ 이미지` → png 선택 | 카드에 이미지가 뜬다. `img src` 가 `/api/blob?pathname=…` |
| 2 | **원본 URL 직접 접근** | Vercel → Storage → Blob 에서 방금 객체의 URL 복사 → 새 탭 주소창에 붙여넣기 | **열리지 않는다** (403/404) |
| 3 | **재요청 304** | 개발자도구 Network 열고 새로고침 → `/api/blob?pathname=…` 행 확인 | `304` · 요청 `If-None-Match` 와 응답 `ETag` 일치 · `Cache-Control: private, no-cache` |
| 4 | **삭제 시 객체 소멸** | 이미지 블록 `✕` → 800ms 뒤 저장 → Blob 대시보드 새로고침 | 객체가 사라진다. Network 의 canvas PUT 응답에 `removedBlobs: 1` |
| 5 | OIDC 경로 | Network 에서 `POST /api/blob/upload` 응답 JSON 확인 | `auth: "oidc"` (OIDC 미사용 프로젝트면 `"token"` — 둘 다 정상) |

**실패 시 볼 곳**

- 4번에서 객체가 남아 있으면 canvas/doc PUT 응답의 **`blobDeleteError`** 필드에 원인이 담긴다(이번에 추가).
- 1번에서 이미지가 안 뜨면 화면에 "권한이 없거나 파일이 삭제됐을 수 있습니다 + [다시 시도]" 가 나온다.
  이때 Network 의 `/api/blob` 응답 코드를 함께 전달하면 401(세션)/404(권한·경로)/기타를 구분할 수 있다.
- 업로드가 503 이면 그 환경에 자격 증명이 없다는 뜻이다(`BLOB_STORE_ID` 포함).

> 위 5건의 **앞단**(인증·인가·경로 규칙·응답 헤더·삭제 대상 산출)은 §4-1·4-2 에서 전부 검증했다.

## 6. 비용 메모

Private 은 Function 경유라 공개 저장보다 전송 비용이 높다(014a).
업로드 상한 10MB 를 유지해 "100MB 초과 파일을 이 경로로 서빙하지 않는다"는 조건을 자동으로 만족한다.
같은 이미지 재요청은 `ETag` + `304` 로 본문 전송을 피한다.

## 7. Preview 버그 대응 — P1 앱 내 이미지 표시 실패 (2026-08-05)

### 7-1. 원인 — 인가 규칙이 아니라 **순서** 문제였다

팀장 가설이었던 "프로젝트 멤버십 요구"는 **해당 없음**이다.
`lib/blob-access.ts` 의 프로젝트 분기에는 멤버십 조건이 애초에 없다
(`project_canvas` 참조 확인 + `project.is_active` 뿐). 화면의 "멤버 없음" 표기는 권한과 무관하다.

실제 원인은 **읽기가 저장보다 먼저 일어난 것**이다.

```
＋ 이미지 → 업로드 성공(객체 생성) → setBlocks(pathname)
   → <img src="/api/blob?pathname=…"> 즉시 마운트 → GET 발사      ← 여기
   → 800ms 뒤에야 캔버스 PUT 저장                                  ← 참조는 이때 생김
```

읽기 권한은 "그 pathname 이 엔티티에 **저장돼 있는가**"로 판정한다.
GET 시점에는 아직 저장 전이라 `canReadBlob` 이 정당하게 거부했고, 그 결과가 404 였다.
업로드·삭제가 멀쩡했던 이유도 같다 — 둘 다 저장된 상태를 기준으로 동작한다.

**단계 판별 근거** — 로그를 분리한 뒤 재현한 결과

```
[blob] storage error — pathname=projects/1/canvas/…-timeline_h.png   ← 저장된 참조: 인가 통과
[blob] denied by access check — user=1 scope=project:1 pathname=…    ← 미저장 참조: 인가에서 거부
```

### 7-2. 수정 (권한 규칙은 그대로)

| # | 수정 | 파일 |
| --- | --- | --- |
| 1 | **참조를 먼저 저장한 뒤 이미지를 그린다** — 업로드 → 즉시 저장(디바운스 건너뜀) → 저장 성공 후에만 pathname 을 화면 상태에 반영. 저장 실패 시 블록을 되돌리고 알린다 | `ProjectCanvas.tsx` · `DocEditor.tsx` |
| 2 | **설명·코멘트 마크다운 이미지도 참조로 인정** — `task.doc` 만 보던 판정에 `task.description` · `task_comment.body` 문자열 포함을 추가. 이전에는 설명/코멘트에 넣은 이미지가 **영구 404** 였다(같은 뿌리의 두 번째 결함) | `lib/blob-access.ts` |
| 3 | **코멘트 첨부 미리보기는 서버를 읽지 않는다** — 아직 코멘트가 없어 참조가 성립하지 않으므로 로컬 `objectURL` 로 그린다 | `SignalThread.tsx` |
| 4 | **1회 자동 재시도** — 저장 직후의 잔여 타이밍을 흡수하는 안전망(600ms 뒤 1회). 두 번째도 실패하면 그대로 사유를 보여준다 | `BlobImage.tsx` |
| 5 | **단계별 로그** — 응답은 404 로 통일하되(비노출 정책 유지), 로그에 `denied by access check` / `storage error` 를 남긴다. 이게 없어서 이번 원인 추적이 늦었다 | `app/api/blob/route.ts` |

권한 판정 조건은 **느슨해지지 않았다.** 2번은 "실제로 참조된 자리"를 빠뜨린 것을 채운 것이고,
소유자·리드·팀 공개 여부와 무관하게 규칙은 그대로다.

### 7-3. 회귀 방지 테스트 — `scripts/verify-blob-access.mjs` (`npm run verify:blob`)

응답이 정책상 전부 404 라 서버 로그로 단계를 가른다. 검증에 쓴 데이터는 스스로 원복한다.

| 검사 | 결과 |
| --- | --- |
| 저장 전 → 인가에서 거부 | O (`denied`) |
| **저장 후 → 인가 통과 (멤버 없는 프로젝트에서 소유자·리드가 읽을 수 있다)** | O (`authorized`) |
| 블록 삭제 후 → 다시 거부 | O |
| 업무 문서: 저장 전 거부 / 저장 후 통과 | O |
| **설명 마크다운 참조 → 통과** (P1 후속) | O |
| **코멘트 마크다운 참조 → 통과** (P1 후속) | O |
| 코멘트 삭제 후 → 다시 거부 | O |
| 다른 프로젝트의 미참조 경로 → 거부 | O |
| 세션 없음 → 401 유지 | O |
| 검증 데이터 원복 | O (캔버스 `["text","text"]` · 업무 84 doc 0 · 설명 19자 — 검증 전과 동일) |
