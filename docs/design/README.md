## 승인 범위를 넘는 판단의 기준 (MD-P-2026-026 §A 회신 [규칙])

작업 중에 지시 범위 밖의 것을 발견했을 때 어디까지 스스로 하는가.

| 상황 | 판단 |
| --- | --- |
| **규격 통일 작업 중, 같은 규격을 어기는 곳을 추가로 발견** | **진행하고 보고한다.** 승인을 기다리지 않는다 |
| 새 기능 | 승인을 먼저 받는다 |
| 새 규칙 | 승인을 먼저 받는다 |
| 데이터 변경 | 승인을 먼저 받는다 |
| 파일 삭제 | 승인을 먼저 받는다 |

**근거가 된 사례.** MD-P-2026-026 §A 는 승인된 표에 없던 `HomeView.BlockEmpty` 를
함께 이관했다. 그 자리는 홈 위젯 넷이 공유하는 자체 빈 상태였고 코랄 버튼을 그렸다 —
홈이 전부 비면 한 화면에 주 액션이 넷 떴다. 승인 표에 없다는 이유로 남겼다면
"섹션에 버튼 금지"라는 규격을 세운 그 커밋이 규격 위반을 그대로 내보냈을 것이다.

규격을 세우는 작업에서 **절반만 적용한 상태**가 가장 나쁘다.
어느 쪽이 기준인지 알 수 없게 되고, 남은 쪽은 반드시 낡는다.

## 마이그레이션은 푸시 전에 멈춘다 (MD-P-2026-027 §B 회신 [정정])

**푸시가 곧 프로덕션 스키마 변경이다.** 그래서 "보고에 명시"로는 부족하다 —
명시했더라도 이미 나간 뒤라면 되돌릴 대상이 프로덕션이 된다. 명시가 아니라 **정지**가 필요하다.

| 순서 | 할 일 |
| --- | --- |
| 1 | 코드 · 마이그레이션 SQL · 롤백 스크립트를 준비하고 **로컬 검증까지만** 한다 |
| 2 | 커밋은 하되 **main 에 푸시하지 않는다.** 작업 브랜치에만 둔다 |
| 3 | 보고 **첫 줄**에 `마이그레이션 포함 — 푸시 대기 중` 과 무엇이 바뀌는지 적는다 |
| 4 | **승인을 받은 뒤에** 푸시한다 |

로컬 검증은 왕복이다 — 적용 → 롤백 → 재적용. 롤백은 **데이터가 있으면 멈춰야** 한다
(0025 · 0027 이 그렇게 돼 있다). 조용히 버리는 롤백은 롤백이 아니다.

## 지시서가 기존 관례와 다르면 — **관례를 따르고 보고한다** (§G · MD-P-2026-031 §C 회신 8)

지시서의 빈 상태 예시가 `아직 업무가 없습니다` 였다. 앱에는 이미 **스무 곳 넘게**
`…없어요` 가 있었다. 예시대로 세 문장만 넣었으면 한 화면 안에서 말투가 갈렸을 것이다.
관례를 따르고 그 사실을 보고했고, PM 이 "그건 규격이 아니라 예시였다"고 확인했다.

> **규칙.** **앱에 이미 여러 곳의 관례가 있으면 그것이 규격이고, 지시서보다 세다.**
> 지시서는 **새 규칙을 만들 때 이기고, 기존 규칙을 모를 때는 진다.**
> 다르면 **관례를 따르고 반드시 보고한다** — 말없이 따르면 지시가 무시된 것이 되고,
> 말없이 지시를 따르면 화면이 갈라진다.

판별은 개수로 한다. 한두 곳이면 관례가 아니라 그냥 먼저 쓴 것이다.

## 우선순위 — 시안보다 §G 규격이 위다

시안은 **배치 의도 참고용**이다. 충돌하면 아래 순서로 따른다.

1. **§G 완성도 규격**(폰트 6단 · 라운드 3종 · 그림자 2단 · 4px 배수 · 대비 4.5:1) — 항상 최우선
2. **지시서 본문의 수치**
3. 시안

시안이 §G 규격을 어기면 **시안이 틀린 것이다.** 시안을 따르지 말고 규격대로 구현한 뒤,
정정 내용을 이 문서에 기록한다. (MD-P-2026-021 후속 ③ 결정)

## PageShell 슬롯 규격 (MD-P-2026-022 §A 승인)

뼈대 순서는 고정이다 — **브레드크럼 → 제목+액션 → 탭 → 필터바 → 본문**.

| 슬롯 | 넣는 것 | 넣지 않는 것 |
| --- | --- | --- |
| `title` | 문자열, **인라인 편집 입력 · 상태 칩 · 목표 링크** | 버튼 · 탭 · 필터 · 드롭다운 |
| `subtitle` | 문자열, 상태 칩 · 목표 링크 | 조작 요소 전부 |
| `actions` | 버튼 · 메뉴. **코랄 주 액션은 화면당 1개** | 필터 |
| `tabs` | 화면 내 보기 전환 | 필터 |
| `filters` | 필터 칩·셀렉트. **선택 슬롯** | 액션 버튼 |

`title`/`subtitle` 이 `ReactNode` 인 것은 프로젝트 상세의 제목 인라인 편집 때문이다.
조작 요소를 넣으면 슬롯 구분이 무너지므로 위 표를 벗어나는 노드는 넣지 않는다.
페이지 레벨 필터가 없는 화면(예: 활동 — 필터를 좌측 레일로 둔다)은 `filters` 를 넘기지 않는다.

### 본문 래퍼 (`pg-legacy`) — 지우지 말 것

기존 화면의 본문 CSS는 거의 전부 `app/home.css` 에 **`.hv …` 로 스코프**돼 있다.
뼈대를 씌우면서 `.hv` 래퍼를 지우면 그 화면의 스타일이 통째로 날아간다.
그래서 뼈대 안에서는 본문을 `<div className="hv pg-legacy"><div className="wrap">…` 로 감싼 채 둔다
(`내 업무` 는 같은 목적의 `tv-legacy` 를 쓴다). `app/design.css` 가 여백만 중화한다.

마크업을 옮기지 않고 §G 규격을 맞추는 방법도 같다 — `app/design.css` 의
`.pg-body :is(…) { font-size / border-radius }` 블록에서 **스냅만** 한다.
본문 컴포넌트를 다시 짜지 않는다.

## 업무 키 체계 (MD-P-2026-024 §5) — 확정

### 표시 키

업무는 하위 업무를 포함해 **`#{id}` 단일 형식**만 쓴다.

- `#39` — 최상위 업무
- `#41` — `#39` 의 하위 업무도 똑같이 `#41`

`#39-1` 같은 파생 표기를 **쓰지 않는다.** 하위 업무는 같은 `task` 테이블의 독립된 행이고,
상위가 바뀌거나 떨어져 나와도 키가 변하면 안 되기 때문이다. 파생 표기를 쓰면
상위를 옮기는 순간 링크·브랜치·커밋에 박힌 키가 전부 거짓이 된다.

### 브랜치 이름

```
md-{id}-{짧은-설명}
```

예: `md-39-goal-inherit`, `md-102-playino-import`

### 커밋 메시지

제목 **끝에** 업무 키를 괄호로 붙인다.

```
feat(goals): 프로젝트 목표를 업무가 상속하게 한다 (#39)
```

여러 업무를 한 커밋에 담아야 하면 `(#39, #41)` 로 쓴다.
다만 업무 하나에 커밋 하나가 기본이다.

> 연동(GitHub PR 자동 연결)은 이번 범위가 아니다. 키 체계만 확정해 둔 것이고,
> 나중에 연동을 붙일 때 위 규칙을 그대로 파싱하면 된다.

## 진척 계산 (MD-P-2026-024 §3) — 계산기는 하나

**`lib/progress.ts` 밖에서 진척을 계산하지 않는다.** 화면도, API도, SQL도.

이 규칙이 생긴 이유: 예전에는 프로젝트 진척 공식만 5가지가 따로 돌아서
같은 프로젝트가 `/projects` · `/projects/[id]` · 홈 · 영역 · 링크 카드에서
각각 다른 %로 보였다.

| 규칙 | 내용 |
| --- | --- |
| 1 | `resolution` 이 `canceled`·`duplicate` 인 업무는 **분모에서 뺀다**. 완료로도 미완료로도 세지 않는다. `deferred` 는 분모에 남기고 **미완료(0)** 로 센다. |
| 2 | 하위 업무가 1건이라도 있으면 상위의 진척은 **하위 완료율**이다. 상위의 수동 진척값은 무시하고, 상세 화면에 "하위 업무로 계산 중"을 띄운다. |
| 3 | 프로젝트 진척은 **최상위 업무만** 대상. 하위 업무는 상위를 통해 이미 반영됐으므로 분모에 다시 넣지 않는다. |
| 4 | **목표 진척은 그 목표에 속한 업무 전체의 평균이다. 프로젝트는 그룹핑 단위이며 계산 단위가 아니다. 프로젝트를 통해 이미 세어진 업무는 직접 연결에서 제외한다.** (MD-P-2026-024 회신 확정 문장) |
| 4-a | **상위 목표의 진척은 기간이 지날수록 업무가 쌓여 희석된다. 남은 양이 아니라 '지금까지 등록된 일 중 얼마나 됐는가'로 읽는다.** (MD-P-2026-024 회신 2 확정 ①) |
| 5 | 집계 대상이 0건이면 **`null`** 이다. `0%` 도 `100%` 도 아니다 → 화면은 "집계 없음". **`null` 을 `0` 으로 접지 말 것** — 실제로 났던 결함이다. |

집계 대상에서 빠지는 것: 비활성 · `proposed` · `dropped` · `work_type='routine'` ·
`resolution IN ('canceled','duplicate')`.

TS 쪽(`isCountable` / `taskProgress`)과 SQL 조각(`countableSql` / `taskProgressSql`)은
**같은 뜻이어야 한다. 한쪽만 고치지 말 것.**

### 분모를 화면에 보여준다 (MD-P-2026-024 지시 1)

진척 옆에는 항상 근거가 붙는다 — `업무 14건 기준`.
문구는 `countedLabel()` 하나가 만들고, 집계 대상이 0건이면 `집계 없음` 이다.
`-` 나 `0%` 로 접지 않는다.

| 화면 | 위치 |
| --- | --- |
| 목표 트리 행 · 목표 상세 | 진척 % 오른쪽 |
| 프로젝트 목록 카드 · 프로젝트 상세 · 영역 화면 | 진행률 % 오른쪽 |

스타일은 기존 보조 텍스트 규격(**10.5px · `var(--muted)`**)만 쓴다 — 새 컴포넌트·새 토큰 없음.

### 기간이 끝난 목표 — 마감 기록 (MD-P-2026-024 회신 3 지시 7)

기간 종료일이 지난 목표는 **지금 집계가 아니라 끝난 시점의 기록**을 보여준다.
7월 목표에 8월 업무가 붙거나 프로젝트가 다음 달 목표로 떠나면,
지금 집계는 그 목표의 7월 실적과 아무 상관이 없어지기 때문이다.

| 상황 | 표시 |
| --- | --- |
| 종료일(또는 그 이전 가장 가까운 날) 스냅샷 있음 | `57% · 7/31 마감 기준` |
| 스냅샷 없음 | `기간 종료 · 마감 기록 없음` |

- 종료일 **이후** 스냅샷은 보지 않는다. 그건 마감값이 아니다.
- **어느 경우에도 수동 배지를 붙이지 않는다.** 손으로 넣은 값이 아니라 실제 기록이다.

#### 없는 마감값은 만들지 않는다

스냅샷이 없으면 **없다고 말한다.** 수동값을 넣어 빈칸을 메우지 않는다 —
그건 기록이 아니라 창작이고, 나중에 아무도 그게 추정치였다는 걸 알 수 없다.

실제 사례: 목표 #12(7월 커리큘럼 1차 완성)는 7/31 스냅샷이 없다.
스냅샷 크론이 2026-08-04(`69da8c3`)에 처음 생겨서 7월에는 돌 수가 없었다.
그래서 이 목표는 영구히 `기간 종료 · 마감 기록 없음` 이다. 값을 만들어 넣지 않았다.
8월 말부터는 크론이 매일 쌓고 있으므로 규칙이 자동으로 동작한다.

| 개인 업무 | 전체 | **안 보임** | 안 보임 |
| 개인 메모 (§C) | 전체 | 안 보임 | 안 보임 |
| 개인 일정 (§D) | 전체 | 안 보임 | 안 보임 |

팀장은 개인 목표의 **진척은 보되 그 아래 업무의 제목·내용은 볼 수 없다.**
숫자는 보이고 내용은 안 보인다 — 이 경계가 §A4 의 핵심이다.
`GET /api/goals/{id}` 가 `tasksHidden: true` 와 `countedTasks` 를 함께 준다.
분모("업무 7건 기준")는 유지하고 목록만 빈 배열로 준다.

### `task.visibility` 두 값

| 값 | 뜻 |
| --- | --- |
| `team` | 팀 전체가 본다 (기본값) |
| `private` | **만든 사람만** 본다. 팀장도 못 본다 |

- 기존 행은 전부 `team`. **어떤 업무가 개인이었는지 추정하지 않는다.**
- `private` 는 **프로젝트에 속할 수 없다** (CHECK `task_private_no_project`).
  프로젝트는 팀 단위라, 들어가는 순간 프로젝트 상세·진척·목표 롤업으로 새어 나간다.
- `private` 는 **남에게 배정할 수 없다** (트리거 `trg_task_private_owner`).
  배정하면 받는 사람이 볼 수 없는 업무가 생긴다.
- `private` 는 **개인 목표에만** 붙는다. 팀 목표에 붙으면 팀 진척 분모에 섞인다.

### 소유자는 `created_by` 다

지시서는 인덱스를 `(owner_actor_id, visibility)` 로 적었으나 `task` 에
`owner_actor_id` 는 **없다.** 있는 것은 `created_by` 와 `assignee_id` 뿐이다.
담당은 바뀔 수 있지만 "이건 내 것"의 기준은 바뀌면 안 되므로 **`created_by`** 로 정했다.
인덱스는 `idx_task_owner_visibility (created_by, visibility)`.

### 가시성 조건은 한 곳에만 둔다

    lib/visibility.ts → visibleTaskSql(viewerParam, alias)
    → `(t.visibility = 'team' OR t.created_by = $N)`

조건이 화면마다 흩어지면 한 곳을 빠뜨리는 순간 샌다.
024 에서 진척 계산기를 하나로 모은 것과 같은 이유다.
**클라이언트 필터링 금지** — 목록 쿼리 자체에서 제외한다(§A3).

홈·팀 보고서처럼 **팀 문서**인 화면은 `visibleTaskSql` 이 아니라
`t.visibility = 'team'` 을 쓴다. 내 개인 업무라도 팀 숫자는 아니다.

### 권한 경계는 파라미터를 거부하는 것이 아니라 받지 않는 것으로 만든다

`/api/personal-events` 는 `actorId`·`owner`·`userId` 를 **아예 받지 않는다.**
받아서 거부하는 코드는 언젠가 조건이 느슨해지고, 그때 조용히 열린다.

> **받을 수 있으면 언젠가 쓰이게 된다.
> 권한 경계는 파라미터를 거부하는 것이 아니라 받지 않는 것으로 만든다.**

### 개인 메모 · 개인 일정 (§C·§D)

`note` · `personal_event` 두 테이블. **둘 다 항상 개인이다** — `visibility` 컬럼이 없다.
값이 하나뿐인 컬럼은 규칙이 아니라 장식이고, 공개 스위치를 달면 다시
"이걸 올리면 남들이 보나?"를 판단해야 한다. 그게 이번 지시가 없애려는 것이다.

가시성 조건도 따로 없다 — 모든 쿼리에서 `owner_actor_id = $viewer` 가 곧 조건이다.
`/api/personal-events` 는 **`actorId` 같은 파라미터를 아예 받지 않는다.**
받을 수 있으면 언젠가 쓰이게 된다.

- 메모 본문은 업무 문서(`task.doc`)와 같은 블록 모델이다. `DocEditor` 를 그대로 쓴다
  (`endpoint` 프롭으로 저장 위치만 바꾼다). 자동저장 800ms·`baseUpdatedAt` 낙관적 동시성 동일.
  편집기를 포크하면 두 규칙이 갈라지고, 갈라진 쪽은 반드시 낡는다.
- 메모·개인 일정은 **활동 로그를 남기지 않는다.** 남기면 제목이 없어도
  "누가 메모를 만들었다"가 팀에 보인다.
- 개인 캘린더는 **새 화면이 아니다.** 기존 캘린더에 "내 일정" 레이어를 켜고 끈다.
  일정은 점선 스팬 바, 개인 업무 기한은 점 — 새 색을 만들지 않고 중립 `--slate` 하나만 쓴다.
  (영역 색은 팀 업무의 소속을 뜻하는데 개인 일정에는 영역이 없다)

### 안 보이는 것은 404 다

남의 개인 업무 id 를 직접 호출하면 **403 이 아니라 404**.
403 은 "그 id 는 존재한다"를 알려주는 셈이다.
상세·문서 본문·코멘트·수정 전부 404 로 맞춰 뒀다.
메모·개인 일정도 같다 — 조회·수정·삭제 전부 404.

## 업무 ↔ 목표 연결 모델 (MD-P-2026-024 회신 6 [확정])

**업무를 개별로 월 목표에 연결한다.** 프로젝트 1:1 연결은 채택하지 않는다.

이 팀의 목표 트리는 **과제 단위**(월 목표 1개 = 과제 1개)이고 프로젝트는 **제품 단위**라
프로젝트↔목표가 1:다이다. 프로젝트를 목표에 붙이면 한 제품의 모든 업무가
관계없는 과제에 섞여 들어간다.

- 프로젝트는 **그룹핑 단위**로만 쓴다. 진척 계산 규칙(업무 평균)은 그대로다.
- 프로젝트→목표 연결 기능은 **폴백으로 남긴다.** 기본 경로가 아니다.
- 업무의 목표 후보 기본값 = **이번 달 월 목표**, 최근 사용 순 (지시 20-1).
  `/api/meta/selectors` 의 `monthGoals` 가 이 순서로 내려온다.
- 소속 프로젝트에 월 목표가 붙어 있으면 **그 목표를 첫 후보로 올리고 `제안` 배지를 붙인다** (지시 20-2).
  재료는 `goalLinkInfo()` 의 `projectGoalId` · `projectGoalTitle`.
  폴백일 뿐이므로 자동 선택하지 않는다 — 순서와 표시만 바꾼다.

### `task.goal_source` 세 값

| 값 | 뜻 | 집계 | 배너 |
| --- | --- | --- | --- |
| `inherited` | 프로젝트에서 따라온 것. **링크가 없으면 "미지정"**(아직 안 정함) | 링크가 있으면 집계 | 미지정이면 **표시** |
| `manual` | 사용자가 목표를 직접 고른 것. 프로젝트가 바뀌어도 안 움직인다 | 집계 | 제외 |
| `none` | 사용자가 **"목표 없음"**을 명시적으로 고른 것 | **제외** | **제외** |

**목표를 강제하지 않는다.** 목표 없이도 업무를 만들 수 있다(지시 20-4).
운영·잡무는 영역만 갖고 목표 없이 도는 것이 정상이다.

`none` 은 성과 집계에서 빠지지만 **월간 보고의 "수행한 업무"에는 그대로 나온다** (지시 23-4).
성과가 사라지면 안 된다. 월간 보고 쿼리는 `goal_task` 를 조인하지 않으므로 이미 그렇게 동작한다.

연결 자체는 기존 `goal_task`(M:N) 를 그대로 쓴다.

`none` 은 **업무 상세의 목표 편집기에서도 고를 수 있다** (확정 23-3).
일괄 연결 화면에서만 되면 개별 정리를 못 한다. 목표 목록 아래 선으로 끊어 별도 줄로 둔다.
상세의 목표 줄은 `none` 일 때 빈 값이 아니라 **"목표 없음"**으로 표시한다 —
비어 보이면 화면이 계속 붙이라고 조른다.

업무 상세에 있던 *"이 프로젝트는 목표에 연결되어 있지 않습니다 → 프로젝트 연결하기"* 안내는
**제거했다.** 확정 연결 모델에서 채택하지 않은 경로로 사람을 보내는 안내였다.

### 미연결 업무는 한 화면에서 정리한다 (지시 21)

업무를 하나씩 열어 붙이게 하면 아무도 하지 않는다.
목표 화면의 **"목표 미연결 업무"** 패널에서 프로젝트별로 접어보며
행에서 바로 지정하거나, 체크해서 일괄 지정한다. 기한도 같은 행에서 넣는다.
§C 목록 규격(38px · 12.5px)을 그대로 쓰고 새 시각 토큰을 만들지 않는다.

## 표본 가드 — 업무가 적으면 %를 말하지 않는다 (지시 16)

업무 1건(100%)으로 연간 목표가 100% 초록 막대가 된 일이 실제로 있었다.
숫자가 틀린 게 아니라 **표본이 없는 값을 단정해 보여준 것**이 문제다.

| 집계 대상 | 표시 | 막대 | 상태 판정 |
| --- | --- | --- | --- |
| 0건 | `집계 없음` | 안 그림 | `null` |
| 1~2건 | `업무 2건 — 표본 부족` | **안 그림** | **`null`** (온트랙이라 말할 근거 없음) |
| 3건 이상 | `67% · 업무 12건 기준` | 그림 | 판정 |

`MIN_SAMPLE = 3` (`lib/progress.ts`). 집계 대상이 0건인 하위 목표가 있으면
`미집계 하위 3개` 를 함께 띄운다. 기간이 끝난 목표의 **마감 기록에는 이 가드를 적용하지 않는다** —
그건 추정이 아니라 실제 기록이다.

## 한 번만 일어나야 하는 전환은 행을 잠그고 다시 확인한다 (회신 8 지시 26)

신호(결정) → 업무 전환처럼 **결과가 한 건이어야 하는 동작**은
"읽어서 없으면 만든다"로 짜면 안 된다. `query()` 는 호출마다 풀에서 다른 커넥션을
빌려오므로 요청 A 와 B 가 둘 다 `task_id IS NULL` 을 읽고 각자 만든다.

    ❌  const s = await loadSignal(id)      // 여기서 읽고
        if (s.task_id) return 409           // 여기서 판단하면
        await query(`INSERT INTO task …`)   // 그 사이에 남이 끼어든다

    ✅  await withTx(async (q) => {
          const [row] = await q(`SELECT task_id FROM signal WHERE id=$1 FOR UPDATE`, [id])
          if (row.task_id !== null) return { created: false, taskId: row.task_id }
          …INSERT + UPDATE…
        })

`withTx()` (`lib/db.ts`) 는 **같은 커넥션**에서 실행해 준다. 잠금이 다음 쿼리까지
이어지지 않으면 `FOR UPDATE` 는 아무 의미가 없다.

실측 (동시 4건 × 10라운드, 로컬):

| | 결과 |
| --- | --- |
| 잠금 없음 | 10/10 라운드에서 중복 — 응답 `[200,200,200,200]`, 업무 **4건** |
| 잠금 있음 | 0/10 — 응답 `[200,409,409,409]`, 업무 **1건** |

**막았으면 갈 곳을 줘야 한다.** 409 응답에 기존 `taskId`·`taskTitle` 을 실어 보내고,
화면은 전환 버튼 자리를 **"업무 #NN 보기"** 로 바꾼다. 버튼을 그냥 숨기면
"왜 없지?" 가 되고, 남겨두면 두 번 눌린다.

> 같은 작업 중 발견 — 이 전환 경로는 `area_id` 를 채우지 않아
> `trg_task_area_match` / NOT NULL 에 걸려 **모든 전환이 500 으로 실패하고 있었다.**
> 중복 이전에 기능 자체가 죽어 있었다. 함께 고쳤다.

## 파괴적 SQL 의 기본 가드 — 건수 일치 (MD-P-2026-024 회신 5)

DELETE·UPDATE 를 담은 SQL 에는 **"승인 시점 건수 = 실행 시점 건수" 가드를 반드시 넣는다.**
다르면 트랜잭션을 죽인다.

```sql
DO $guard$
DECLARE n int;
BEGIN
  SELECT count(*) INTO n FROM <대상> WHERE <조건>;
  IF n <> <승인 시점 건수> THEN
    RAISE EXCEPTION '중단 — 대상 건수가 승인값과 다릅니다. 실제 % (기대 %)', n, <승인 시점 건수>;
  END IF;
END $guard$;
```

### 왜 이것이 기본인가

"대상에 잘못된 행이 섞였는가" 류의 가드는 **대상을 그 조건으로 뽑는 순간 논리적으로 항상 0** 이라
아무것도 막지 못한다. 예: 대상을 `is_demo = true` 로 뽑고서 "`is_demo = false` 가 섞였는가"를 물으면
언제나 0건이다.

실제로 막아주는 것은 **건수가 승인 시점과 같은가** 뿐이다.
데이터가 승인 이후 바뀌었거나, 애초에 다른 DB 를 보고 있었거나, 조건이 의도와 다르게 걸렸을 때
전부 이 가드에 걸린다. (MD-P-2026-024 에서 로컬 기준으로 쓴 삭제 SQL 이
프로덕션과 대상이 다르다는 것을 이 가드만이 잡아낼 수 있었다)

### 함께 지킬 것

- `BEGIN` 으로 시작하고 `COMMIT` 은 파일 끝에 **주석 처리**해 둔다. 사람이 눈으로 보고 푼다.
- 삭제 **전** 대상 건수를 세는 `SELECT` 를 같은 파일 앞부분에 둔다.
- 가드는 `DO` 블록 + `RAISE EXCEPTION` 으로 쓴다.
  `CASE … ELSE 1/0` 은 Postgres 가 상수를 미리 접어 조건과 무관하게 터진다.
- **다른 DB(로컬·복제본)에서 통과했다는 것은 프로덕션 안전의 근거가 아니다.**
  대상 데이터가 있는 그 DB 에서 건수를 확인하고 나서 쓴다.

## 화면 실측 보고 규격 (MD-P-2026-024 지시 8)

폰트·라운드만 재면 **레이아웃 붕괴를 못 잡는다.**
실제로 MD-P-2026-022 §A 1~4 에서 목표 트리가 통째로 깨졌는데
"§G 위반 0건"으로 보고된 적이 있다. 캐럿 SVG 가 11px → 1108px 로 부풀어
화면을 덮고 있었지만, 폰트도 라운드도 규격 안이었기 때문에 표에 잡히지 않았다.

그래서 모든 화면 실측표에 아래 **3항목을 반드시 포함한다.**

| 항목 | 무엇을 재나 | 왜 |
| --- | --- | --- |
| `scrollHeight` | `document.body.scrollHeight` | 붕괴하면 비정상적으로 커진다 (997px → 2982px) |
| 최대 요소 3개 | 폭·높이 상위 3개 요소와 그 크기 | `svg.cv 1108px` 같은 값이 바로 드러난다 |
| 육안 확인 | 캡처를 **실제로 열어** 봤는지 | 안 봤으면 "확인 안 함"이라고 쓴다. 비워두지 않는다 |

세 번째가 핵심이다. **캡처를 저장만 하고 열어보지 않는 것은 확인이 아니다.**
확인하지 않았으면 그 사실을 적는다 — 침묵은 확인했다는 뜻으로 읽힌다.

계측은 `scripts/measure-screens.mjs` 로 한다(위 3항목이 기본 출력이다).

### 캡처 라벨은 파일명이 아니라 화면에서 읽은 값으로 단다

(MD-P-2026-027 §A 회신 [확정])

캡처를 남길 때 라벨에 **화면에서 실제로 읽은 값**을 적는다 —
쪽수 `"2 / 3"`, 건수 `"11건"`, 상태 칩 문구 등.
**캡처를 열지 않아도 로그만 보면 어긋난 것이 드러나야 한다.**

    ✗  03-firstrun-2   첫 사용 안내 2/3
    ○  03-firstrun-2   첫 사용 안내 — 화면에 표시된 쪽수 "2 / 3"

**이 규칙이 생긴 이유.** 워크스루 스크립트가 "다음" 버튼을 모달 밖에서 찾아
슬라이드가 그대로인데 넘어간 줄 알았고, **1장을 세 번 찍어 놓고 "3장 모두 뜸"으로 보고**했다.
파일명은 `-1 · -2 · -3` 이라 로그만 봐서는 멀쩡했다.
화면에서 읽은 쪽수를 라벨에 넣었으면 첫 줄에서 드러났을 것이다.

### 데이터를 비우는 점검 스크립트는 백업·복원을 갖추기 전에 실행하지 않는다

(MD-P-2026-026 §A 회신 [확정])

빈 상태·오류 상태는 **데이터를 실제로 비워야** 띄울 수 있다. 그래서 점검 스크립트가
DB 를 건드린다. 규칙은 하나다 — **비우기 전에 되돌릴 방법이 있어야 실행한다.**

| | 방법 |
| --- | --- |
| `is_active` 가 있는 표 | `UPDATE … SET is_active = false` → `finally` 에서 `true` |
| 없는 표 | `CREATE TABLE _bk_x AS SELECT * FROM x` → 삭제 → `finally` 에서 되넣고 `DROP` |
| 트랜잭션 | **쓰지 않는다.** 앱은 자기 커넥션으로 읽으므로 `BEGIN` 안의 변경은 안 보인다 |
| `TEMP TABLE` | **쓰지 않는다.** 풀에서 매번 다른 커넥션이 나와 다음 쿼리에서 사라진다 |

복원은 반드시 `finally` 에 둔다. 중간에 실패해도 원래대로 돌아와야 한다.

**이 규칙이 생긴 이유.** `scripts/capture-empty-states.mjs` 초기 버전이
`DELETE FROM saved_item` · `DELETE FROM agent_job` 를 복원 없이 실행해
로컬 시드 4행을 잃었다. 프로덕션이었으면 되돌릴 수 없었다.

## 빈 상태 2단 규격 (§G) — 전체 / 섹션 (MD-P-2026-025 회신 [확정 B-7])

빈 상태를 **한 규격으로 다루면 안 된다.** 화면 전체가 비는 것과
페이지 안의 한 블록만 비는 것은 다른 상황이고, 후자에 96px 아이콘을 넣으면
월간 보고 같은 화면이 아이콘 밭이 된다.

**판단 기준: 그 화면에 그것 말고 볼 게 없으면 전체, 다른 게 있으면 섹션.**

### 전체 빈 상태 — 페이지 본문 전체가 빔

| | 값 |
| --- | --- |
| 구성 | 아이콘 88px + 제목 + 설명 + CTA |
| 컴포넌트 | `EmptyState` |
| 정렬 | **자기 박스 안에서** 세로 가운데 |
| 최소 높이 | **320px** |
| 여백 | 위아래 **최소 48px** |

**화면 정중앙으로 내리지 않는다** (MD-P-2026-026 §A 회신 [확정]).
뷰포트 한가운데에 놓으면 브레드크럼·제목·탭에서 멀어져 본문이 붕 뜬다.
`min-height: 320px` 은 짧은 화면에서 위에 딱 붙는 것만 막는 값이다.

### 세 가지 동시 표시 금지 (MD-P-2026-026 §A 회신 [확정])

캡처를 열어 보고서야 잡은 것들이다. 타입체크·빌드는 전부 통과한 상태였다.

**① 오류가 떠 있으면 목록도 빈 상태도 렌더하지 않는다.**
화면이 "못 불러왔다"와 "없다"를 동시에 말하면 안 된다.
`/tasks` 는 500 을 받은 자리에서 "업무를 불러오지 못했어요" 아래에
"아직 업무가 없어요 + ＋새 업무" 를 같이 띄우고 있었다.

**② 전체 빈 상태가 떠 있으면 헤더의 같은 동작 액션을 숨긴다.**
코랄 채움은 **화면당 1개**이고, 빈 상태가 떠 있을 때 그 1개는 **빈 상태의 CTA** 다.
`/tasks` · `/handover` · `/notes` · `/signals` 가 헤더와 빈 상태에
같은 동작의 코랄 버튼을 둘씩 그리고 있었다.

**③ 그리드 안의 섹션 빈 상태는 전폭 span 한다.**
셀 하나에 끼면 좁은 폭에 갇혀 세로로 늘어난다.
홈 히어로 타임라인의 빈 상태가 76px 이름칸에 끼어 **세로 189px** 이 됐다 (규격 38~56px).
어두운 배경 위에 놓이는 경우 **대비 4.5:1 을 따로 확인한다** — 주변 보조 문구의
투명도를 그대로 물려받으면 본문인데 보조 문구만큼 흐려진다.

### 섹션 빈 상태 — 페이지 안의 한 블록·탭·목록만 빔

| | 값 |
| --- | --- |
| 구성 | **아이콘 없음.** 한 줄 문구만 |
| 컴포넌트 | `SectionEmpty` — 하나로 통일한다 |
| 글자 | 12.5px · `var(--muted)` |
| 높이 | 38~56px |
| 정렬 | 그 섹션의 본문 정렬을 따름 |
| 행동 | 필요하면 문장 끝에 **텍스트 링크 하나.** 버튼을 쓰지 않는다 |

`.gempty` · `.dl-empty` · `.rp-empty` 같은 **개별 클래스를 새로 만들지 않는다.**
지금 흩어져 있는 것들은 규격이 없어서 각자 생긴 것이지 의도한 차이가 아니다.

### 로딩·오류는 빈 상태가 아니다

"불러오는 중…"과 "불러오지 못했어요"는 **데이터가 없는 것이 아니라 아직/못 온 것**이다.
같은 클래스를 돌려쓰면 셋이 구분되지 않는다. 위 두 규격의 대상이 아니다.

## 색면은 세 가지뿐이다 (§G · MD-P-2026-026 §B-3)

페이지·카드 배경에 쓸 수 있는 값은 **`--bg` · `--surface` · `--surface-2`** 셋뿐이다.

| 토큰 | 값 | 쓰는 곳 |
| --- | --- | --- |
| `--bg` | `#F7F8F9` | 페이지 캔버스 · 상단 바 |
| `--surface` | `#FFFFFF` | 카드 · 목록 · 패널 |
| `--surface-2` | `#FBFCFC` | 목록 헤더 · 스켈레톤 · 짝수행 · 보조 블록 |

**예외는 두 종류뿐이다.**

| 예외 | 예 |
| --- | --- |
| 의도된 다크 그라데이션 | 사이드바 · 홈 히어로 |
| 의미색 틴트 배너 | `--amber` 8~12% (안내), `--coral-bg` (선택·리스크) |

### 오버레이는 색면이 아니다 — `--glass`

| 토큰 | 값 | 쓰는 곳 |
| --- | --- | --- |
| `--glass` | `rgba(22,25,29,.02)` | 카드 상단 미세 그라데이션 · hover 바탕 · 칩 배경 |

**세 색면 중 하나 위에 얇게 얹는 중성 오버레이**다. 웜톤이 아니고, **단독 배경으로 쓰지 않는다.**
그라데이션 인자(`linear-gradient(var(--glass), transparent)`)로 쓰이는 자리가 있어
불투명 토큰으로 치환할 수 없다. 규격에 없는 값이 61곳에 남아 있는 상태를 만들지 않으려고
정식 등재했다 (MD-P-2026-026 §B-3 회신 [확정]).

### 배경 검사는 `background-image` 까지 본다

첫 실측이 **가장 큰 위반을 놓쳤다.** `body` 의 `background-color` 는 `--bg` 였고
토큰 검사를 통과했는데, 실제 아이보리는 `background-image` 쪽에 있었다.

    body { background-color: var(--bg);
           background-image: linear-gradient(180deg, #F8F6F1 0%, #F3F0E8 100%); }

**전 화면(21/21)의 캔버스가 아이보리**였고 그 위 카드만 순백이라,
화면마다 두 톤이 섞여 보였다. 검사가 한 속성만 보면 다른 속성으로 새어 나간다.

### backdrop-filter 는 배경이 불투명해지면 함께 뺀다

투명한 상단 바를 위해 붙였던 `backdrop-filter: blur()` 가 배경을 불투명하게 바꾼 뒤에도
남아 있었다. 흐릴 대상이 없는데 남아 있으면 Chromium 이 페이지를 합성 레이어로 올려
**글자 안티에일리어싱이 서브픽셀 → 그레이스케일로 바뀐다.**
효과는 없고 렌더링만 달라지는 코드다.

## 스타일이 한 스코프 안에만 있으면 다른 화면에서 벌거벗는다 (§B-1)

`.lk` · `.seg` 는 `app/home.css` 의 **`.hv` 스코프 안에만** 정의돼 있었다.
PageShell(`.pg-body`)을 쓰는 화면에서 같은 클래스를 붙이면
CSS 가 하나도 닿지 않아 **브라우저 기본 버튼**(회색 각진 박스)이 그대로 그려졌다.

    /projects/1  "＋ 링크" · "Notion 문서 만들기"
    /signals 결정 "원본 논의 →" ×3
    /activity   "저장" · 채널 세그먼트 2개

클래스는 붙었으니 코드만 읽어서는 멀쩡해 보인다. **화면을 띄워야 보인다.**

**규칙 두 가지.**
1. 공용 컨트롤 클래스는 **스코프 없이** 정의한다. 레거시 스코프를 덮어야 하면
   `:is(.hv, .pg-body) .x` 처럼 같은 무게로 함께 잡는다.
2. 점검 스크립트는 **브라우저 기본 스타일이 남아 있는지**를 본다 —
   `border-style: outset/inset` 또는 `background: rgb(239,239,239)` 가 그 신호다.
   원인이 무엇이든 "CSS 가 이 요소에 닿지 않았다"를 잡아낸다.

## 자료의 정식 경로는 세 곳뿐이다 (MD-P-2026-027 B11-d)

자료는 **업무 첨부(Blob) · 프로젝트 캔버스의 링크 · Notion** 세 곳에 둔다.
**영역 단위 자료 화면은 두지 않는다. 저장 위치를 늘리면 아무 데도 안 쌓인다.**

| 무엇 | 어디 | 테이블 |
| --- | --- | --- |
| 업무에 딸린 파일·캡처 | 업무 상세 패널의 첨부 | `artifact` + `task_artifact` (인수인계 화면이 읽는다) |
| 프로젝트의 참고 링크 | 프로젝트 캔버스의 링크 블록 | `external_link` · 캔버스 문서 블록 |
| 문서·회의록 본문 | Notion | 앱은 링크 메타데이터만 (본문을 가져오지 않는다) |

네 번째 자리였던 영역 자료 탭은 만들어 놓고 **한 번도 쓰이지 않았다** —
삭제 시점 실측이 `artifact` 0 · `task_artifact` 0 · `external_link` 0 이었다.
자리를 늘린다고 자료가 모이지 않는다. 어디에 둘지 고민하게 만들면 아무 데도 안 둔다.

`/areas/{id}` 경로는 `/tasks?area={id}` 리다이렉트로 **남긴다** — 이미 돌아다니는 북마크가 죽지 않게.

## 만드는 자리와 고치는 자리를 나눈다 (MD-P-2026-027 §C · §D)

**업무를 만드는 곳은 등록 모달 하나다.** 오른쪽 상세 패널(420px)은 이미 있는 업무를
보고 고치는 용도로만 쓴다. 예전에는 패널이 둘을 겸했고, 그 폭에 생성 폼을 욱여넣느라
설명이 4줄 textarea 였으며 "만든 뒤 상세에서 목표를 연결하세요" 라는 안내가 붙어 있었다 —
만들 때 정할 수 있는 것을 나중으로 미룬 것이다.

| 자리 | 규격 |
| --- | --- |
| 등록 모달 | 720×560 · 최대 90vh · 중앙 · `--scrim`. 왼쪽=제목(19px)+본문, 오른쪽 220px=속성 |
| 속성 순서 | 공개 범위 · 프로젝트 · 목표 · 담당 · 상태 · 우선순위 · 기한 · 영역 |
| 하단 | 취소 · "만들고 계속 추가" · 만들기 (**코랄은 만들기 하나**) |
| 조작 | 열 때 제목 포커스 · ⌘Enter 저장 · Esc 닫기(내용 있으면 확인) |
| 한 줄 입력 | Enter = 제목만으로 즉시 생성 / ⌘Enter = 친 내용을 들고 모달로 확장 |

**"만들고 계속 추가"는 프로젝트·목표·담당을 유지하고 제목·본문만 비운다.**
전부 비우면 같은 묶음을 연달아 넣을 때 매번 다시 고르게 된다 — 그럴 바엔 껐다 켜는 게 낫다.

**본문 편집기를 포크하지 않는다.** 모달의 본문은 서식만 있는 축약판이다.
슬래시 명령·임베드는 없다 — 아직 존재하지 않는 업무에는 붙일 문서가 없다.
업무가 생기고 나면 DocEditor 가 이어받는다.

**목표 연결은 생성 직후 PATCH 로 붙인다.** POST 에 `goalIds` 를 새로 받게 하면
개인/팀 목표 교차 금지 규칙(§B3)이 두 벌이 된다. 규칙이 두 벌이면 한쪽이 반드시 낡는다.

### 연결은 행위가 아니라 자리다 (§D)

프로젝트에 붙이는 일을 **별도 작업으로 남기지 않는다.** 만들고 나서 붙이는 게 아니라,
붙어 있는 자리에서 만든다. 그래서 같은 한 줄 입력이 두 곳에 있다 —
업무 목록 맨 위(§C3)와 **프로젝트 상세의 업무 목록 맨 아래**(§D2). 후자에서 만들면
프로젝트가 자동으로 지정된다.

프로젝트 셀렉트는 검색형 콤보박스다. 타이핑으로 좁히고, 최근 사용이 위로 오고,
일치가 없으면 맨 아래 "'…' 새 프로젝트로 만들기" 가 뜬다.
**그 줄은 팀장에게만 그린다** — `POST /api/projects` 가 팀장 전용이라,
팀원에게 보여 주면 눌러도 403 이 나는 버튼을 보여 주는 셈이다.

새 프로젝트는 **그 업무의 영역을 물려받는다.** 영역 없는 프로젝트를 만들면
영역 필터(B11-3)에서 영원히 안 보인다.

### 검사 스크립트는 자기가 만든 것만 건드린다

§D3(다중 선택 → 프로젝트 일괄 지정) 검사에서 목록의 앞 두 줄을 그냥 체크했더니,
일괄 지정이 **진짜 업무 2건의 프로젝트를 실제로 바꿔** 버렸다.
정리 단계는 그 업무들이 실측 프로젝트를 참조하고 있어 외래키로 막혔고, 그제서야 드러났다.
이후로는 검사용 행을 직접 만들어 검색으로 좁힌 뒤 고른다.
정리 단계에는 **표식이 없는 행이 실측 대상을 참조하면 이름을 찍고 되돌리는** 그물을 둔다 —
조용히 밀면 무엇을 건드렸는지 영영 모른다.

## 연결 경로는 하나뿐이다 (MD-P-2026-030 §A · §B)

**목표에 붙는 것은 업무뿐이고, 붙는 방법은 `goal_task` 하나뿐이다.**

예전에는 경로가 둘이었다.

    ① 업무 → 목표          goal_task (직접 연결)
    ② 프로젝트 → 목표       project.goal_id  ← 없앴다

경로가 둘이면 같은 질문에 답이 둘 나온다. 실제로 나던 증상:

- 목표 화면 배너는 "미연결 업무"라고 세는데, 그 업무가 진척에는 이미 잡혀 있었다.
  배너는 `goal_task` 만 보고, 진척은 프로젝트 경유까지 봤기 때문이다.
- 프로젝트가 8월 목표를 가리키면 **그 프로젝트의 7월 업무까지 8월 분모에** 들어갔다.
  그 업무는 8월 목표에 붙은 적이 없다.

경로를 지우는 대신 규칙을 더하는 방법(예: "프로젝트 경유는 기간이 겹칠 때만")도 있었다.
그렇게 하면 규칙이 늘고, 어느 화면이 어느 규칙을 쓰는지 다시 갈라진다. **경로를 지웠다.**

### 판정은 조각 하나에서 나온다 (§B1)

`lib/progress.ts` 에 조각을 두고 계산기·분모·배너가 **모두 그것을 읽는다.**

| 조각 | 뜻 |
| --- | --- |
| `goalLinkedSql(t)` | 이 업무가 **어떤** 목표에든 붙어 있는가 |
| `goalLinkedInSql(t, sub)` | 이 업무가 **그 목표 집합**에 붙어 있는가 |
| `goalSubtreeCte(id)` | 그 목표와 살아 있는 모든 자손 (`sub`) |
| `unlinkedTaskSql(t)` | 미연결 = 집계 대상 · 최상위 · 직접 연결 없음 · `goal_source <> 'none'` |

배너 숫자와 일괄 연결 화면의 행은 **같은 배열**에서 나온다. 두 번 세지 않는다 (§B3).
`goalCountedSql()`("업무 N건 기준"의 분모)과 `goalSubtreeTaskInput()`(진척의 입력)도
같은 두 조각으로 짜여 있어, 한쪽만 바뀌는 일이 구조적으로 불가능하다.

### 상속은 없앴다. `goal_source` 는 두 가지만 뜻한다 (§A4)

    none       사용자가 "목표 없음"을 명시적으로 골랐다 — 미연결이 아니다 (지시 23-2)
    그 외       붙일 수 있는 업무. 링크가 없으면 미지정이고 미연결 배너에 오른다

"그 외"에 해당하는 값이 지금 둘이다.

- `manual` — **새로 만들어지는 값.** 새 업무는 전부 이 값이다.
- `inherited` — **역사적 값이다.** 상속 개념이 제거된 뒤로 새로 만들어지지 않는다.
  지금은 '미지정'을 뜻한다. 프로덕션에 19건 남아 있고, **그 값은 유지한다.**
  `CHECK` 를 좁히지 않는다 — 좁히면 남아 있는 행이 제약 위반이 된다.
  이름 정리(`inherited` → `unset`)는 BACKLOG **B-13**.

`task.goal_source` 컬럼의 DB 기본값은 아직 `'inherited'` 다(컬럼은 §A5 에 따라 건드리지 않았다).
그래서 **업무를 INSERT 하는 모든 경로가 `NEW_TASK_GOAL_SOURCE` 를 명시해야 한다.**
명시하지 않으면 새 업무가 역사적 값을 물려받아 조용히 늘어난다.
지금 그 경로는 둘이다 — `POST /api/tasks` 와 신호→업무 전환(`POST /api/signals/[id]`).

### 지우지 않은 것 (§A5)

`project.goal_id` 컬럼과 그 데이터, `goal_task` 테이블, `goal_snapshot.linked_project_count`
전부 그대로다. **읽지 않게만 하고 남겨 뒀다.** 되살릴지는 사람이 판단한다.
`goal_snapshot.linked_project_count` 는 계속 실제 값을 찍는다 —
0 으로 덮으면 지나간 달의 기록까지 거짓이 된다.

## 규격은 검사가 붙어야 성립한다 (§G · MD-P-2026-027 §H3 회신 [기록])

**"스피너 금지"는 오래전부터 적혀 있었다.** 그런데 §H 정적 검사를 처음 돌렸을 때
회전 스피너가 **2건**(`.agf-spin` · `.ma-spin`) 멀쩡히 살아 있었다.
문서가 틀린 게 아니라 검사가 없었을 뿐이다.

같은 실행에서 **142건**이 나왔다 — 허용 목록 밖 속성 29 · 무한 반복 11 · 토큰 아닌 값 102.
전부 규격이 적힌 뒤에 하나씩 들어온 것이고, **코드 리뷰로는 한 번도 안 걸렸다.**
사람은 `transition: .15s` 가 `all` 이라는 것을 매번 알아채지 못하고,
파일 세 개에 흩어진 `.14s` 를 세지 못한다.

> 규격은 문서에 적는 것으로 성립하지 않는다. **검사가 붙어야 성립한다.**

새 규격을 확정할 때는 같은 커밋에서 "이걸 무엇이 검사하는가"를 함께 만든다.
검사를 만들 수 없는 규격은 규격이 아니라 취향이다.

### 검사도 낡는다 (§G 검증 규격)

026 §A-4 는 "스켈레톤 shimmer 금지"였고, 빈 상태 하네스가 "스켈레톤 애니메이션 0"을 단언했다.
027 §H2 가 스켈레톤 **한 곳에** shimmer 를 허용하자, 그 단언이
**정상 동작을 위반으로** 잡았다(`규격위반 2`). 규격이 앞서 갔고 검사가 뒤에 남은 것이다.

| | 규칙 |
| --- | --- |
| 1 | 규격을 바꾸면 **그 규격을 검사하던 하네스를 같은 커밋에서 함께 고친다** |
| 2 | 유보했던 규칙을 확정할 때는 **"이 규칙을 검사하는 곳이 어디인가"를 먼저 찾는다** |
| 3 | 고칠 때는 반대 방향 단언을 함께 넣는다 — "허용된 것이 **있는가**"까지 본다 |

3 이 없으면 완화가 곧 무장해제가 된다. 지금 스켈레톤 검사는
"sk-shimmer 뿐인가 · 아예 없지는 않은가 · reduce 에서 멈추는가" 셋을 함께 본다.

### 측정의 정의도 함께 검토한다

§H4-② "화면 밖에서는 재생하지 않는다"를 처음엔 "% 글자가 1가지"로 단언했다.
그건 "값도 바뀌지 마라"는 뜻이 돼 버린다 — 값은 바뀌어야 하고, **굴러가지만 않으면 된다.**
지금은 1가지=그대로 · 2가지=스냅 · 3가지 이상=굴러감으로 나눠 보고,
화면 밖은 2 이하, 화면 안은 최소 하나가 3 이상(짝이 되는 존재 단언)이어야 통과한다.

### API 상태 코드만 보면 통과하는 결함이 있다 (MD-P-2026-028 §B 회신 [기록])

**화면에서 재야 보인다.**

**실제로 있었던 일.** 028 §B1 의 차단 지정에서, 서버가 돌려준 거절 사유가 이랬다.

    missing FROM-clause entry for table "t"

`visibleTaskSql()` 은 기본 별칭이 `t` 인데 그 쿼리의 `FROM task` 에 별칭이 없었다.
SQL 예외가 그대로 **사용자 화면의 거절 사유 자리에** 떴다.

검사가 API 응답의 상태 코드만 봤다면 통과했을 자리다 — 400/409 는 정상적으로 나왔고,
잘못된 것은 **본문 문장**이었다. 지시서가 "서버가 409 를 준다는 것만으로 부족하다.
가드가 화면에서 어떻게 보이는지 실측할 것" 이라고 못 박은 이유가 이것이다.

**규칙.** 사용자에게 문장을 보여주는 경로는 **그 문장을 읽어서** 검사한다.
상태 코드는 "거절됐다" 까지만 말하고, 무엇이 보이는지는 말하지 않는다.

### 두 도구가 같은 값을 냈다는 것은 정확성의 증거가 아니다 (MD-P-2026-030 §C1 회신 [규칙])

같은 것을 재는 도구를 둘 만들어 대조하면 안심이 된다. 그 안심이 틀릴 때가 있다.

**실제로 있었던 일.** 030 §C1 의 측정을 Node 스크립트와 프로덕션용 SQL 두 벌로 만들고,
로컬에서 돌려 **같은 값이 나오는 것을 확인했다.** 그런데 SQL 쪽 조건이 틀려 있었다.

    적혀 있던 것   (resolution IS NULL OR resolution <> 'deferred')
    맞는 것       (resolution IS NULL OR resolution NOT IN ('canceled','duplicate'))

deferred 는 **미완료로 세는** 것이 규칙인데 빼고 있었고, 분모에서 빼야 할
canceled/duplicate 는 넣고 있었다. 두 값이 같았던 이유는 하나뿐이다 —
**로컬에 deferred·canceled·duplicate 행이 한 건도 없었다.**
두 조건이 갈라지는 데이터가 없으면 두 조건은 언제나 같은 답을 낸다.
대조가 증명한 것은 "두 도구가 같다"가 아니라 아무것도 아니었다.

**규칙.**

1. 두 측정 도구를 대조할 때는, **두 도구가 갈라지는 조건에 해당하는 데이터가
   실제로 존재하는지 먼저 확인한다.** 없으면 그 대조는 아무것도 증명하지 않는다.
2. 조건이 여러 값을 배제·포함하는 쿼리를 쓸 때는, **각 값에 해당하는 행을 하나씩
   만들어 놓고** 대조한다. 있는 데이터로만 맞춰 보면 없는 경우는 영영 안 밟힌다.
3. 대조가 통과했다고 적을 때는 **무엇이 갈라지는 축이었는지**를 같이 적는다.
   "두 도구가 같은 값을 냈다"만 적으면 다음 사람이 이 함정을 그대로 밟는다.

이것은 지시 28(부재 단언 규격)의 같은 병이다. 0건을 세는 것과, 셀 것이 없어서 0건인 것을
구별하지 않으면 검사는 통과하면서 아무것도 지키지 않는다.

## 표본 부족은 값이 없다는 뜻이 아니다 (§G · 지시 16 · MD-P-2026-030 지시 30)

**표본 부족은 "값이 없다"가 아니라 "값의 신뢰도가 낮다"는 뜻이다.
값은 보이고 막대는 그리지 않는다.**

| 집계 대상 | 막대 | 값 | 근거 |
| --- | --- | --- | --- |
| 0건 | 빈 트랙 | `집계 없음` | — |
| 1~2건 | **빈 트랙** | `100%` · `--muted` 로 낮춤 | `업무 1건 — 표본 부족` |
| 3건 이상 | 채움 | `100%` · `--ink` | `업무 14건 기준` |

**값을 감추지 않는 이유.** 값을 지우면 사용자가 상세를 열어야 확인이 된다.
연간 카드는 커서 값이 사라지면 빈 카드로 읽힌다.
**과잉 확신을 만드는 것은 숫자가 아니라 막대다** — 숫자는 읽어야 보이지만
막대는 훑어도 보인다. 그래서 막대만 뺀다.

`.none`(집계 없음)과 `.low`(표본 부족)는 색이 같지만 클래스를 나눠 둔다.
합치면 "값이 없다"와 "값이 흐리다"가 코드에서 구별되지 않는다.

### 판정이 아니라 **표시 결정 전체**를 공유한다

이 규격이 새어 나갔던 자리가 있다. 연간 카드(`YearCard`)가 `GoalProgress` 를 쓰지 않고
막대를 직접 그리느라 `canShowBar()` 를 부르지 않았고, 집계 대상 1건짜리 연간 목표가
**100% 초록 막대**로 떴다. 지시 16 이 막으려던 장면이 정확히 그것이다.

030 §A3 로 프로젝트 경유가 빠지면서 실제로 그 상태에 닿는 목표가 생겼다 —
프로덕션 연간 #8 이 업무 21건 → 1건이 된다. **조건이 바뀌면 여태 안 밟히던 분기가 밟힌다.**

판정 함수(`canShowBar`)만 공유하면 라벨 조립이 또 갈라진다. 그래서
`progressDisplay(progress, counted)` 가 **막대를 그리는지 · 값이 있는지 · 근거 문구 ·
신뢰도 낮음** 넷을 한 번에 낸다. `GoalProgress` 와 `YearCard` 가 같은 함수를 부른다.

    const d = progressDisplay(goal.progress, goal.countedTasks);
    d.drawBar · d.hasValue · d.basis · d.lowConfidence

**규칙.** 규격이 여러 조각으로 표현되는 화면은 조각을 나눠 공유하지 말고
**결정 전체를 한 함수에서 받는다.** 조각만 공유하면 조립하는 곳마다 다시 갈라진다.

> **공유해야 하는 것은 마크업이 아니라 결정이다.**
> 컴포넌트를 합치면 배치가 다른 곳이 깨지고, 판단을 안 합치면 화면이 다른 말을 한다.
> 연간 카드와 월 행은 마크업을 각자 두고 `progressDisplay()` 하나를 함께 쓴다.

## 연결 모델이 바뀌면 한 번은 말한다 (MD-P-2026-030 §C3)

어제까지 프로젝트를 목표에 붙여 두면 진척이 잡혔다. 오늘부터는 안 잡힌다.
**아무 말 없이 숫자만 내려가면 사람들은 고장으로 읽는다.**
데이터를 지운 것이 아니라 세는 방법이 바뀐 것이고, 그 사실을 한 번은 말해야 한다.

규격은 셋뿐이다.

- **한 번만 뜬다.** 닫으면 다시 뜨지 않는다 (`localStorage: tb:notice:link-model-030`).
- **코랄도 앰버도 쓰지 않는다.** 사고도 경고도 아니다. `.ulbanner` 와 같은 중립 톤이다.
- **다음 행동이 한 줄 있다.** "바뀌었습니다"로 끝나면 읽는 사람이 할 일이 없다.

숫자(21건 · 1건)는 화면에서 계산하지 않고 문구에 박았다.
이 안내는 "이번 배포로 무엇이 달라졌는가"를 말하는 것이지 지금 상태를 재는 것이 아니다.
이미 바뀐 뒤에 계산하면 "빠졌다"는 과거를 영영 말할 수 없다.

## 시그니처 모션 두 곳 (§H4 구현 기록)

### ① 홈 다크 히어로 — 켜는 일과 끄는 일을 같은 효과에 두지 않는다

`sessionStorage` 가드가 있는 효과 안에서 "재생 시작"과 "재생 종료 타이머"를 같이 걸었더니,
개발 모드 StrictMode 가 효과를 붙였다 떼었다 다시 붙이는 과정에서
**두 번째 실행이 가드에 막혀 일찍 빠져나갔고, 타이머만 정리되고 다시 걸리지 않았다.**
결과는 `hero-grow` 클래스가 영원히 남는 것 — 실측에서 `2000ms 뒤에도 5개`로 잡혔다.

끄는 일은 **상태를 보고 따로 건다.** 다시 붙어도 다시 걸린다.

클래스를 떼는 것 자체가 안전장치이기도 하다. 붙여 둔 채로 탭이 백그라운드로 가면
애니메이션이 시작되지 않은 바가 `scaleX(0)` 인 채 **영영 안 보이게** 된다.

#### 6개 초과는 **구조적 근거**다 — 실측이 아니다

§H2 는 stagger 를 최대 6개로 제한한다. 실측 시점의 데이터에는 히어로 바가 **5개뿐**이라
7번째 이후가 애니메이션 없이 그려지는 것을 **화면에서 확인하지 못했다.**
근거는 코드다 — `HERO_GROW_MAX = 6` 이고 인덱스가 6에 닿으면 클래스를 붙이지 않으므로,
초과분에는 `animation` 자체가 걸리지 않는다.

§G 규격대로 **실측과 구조적 근거를 구분해 적는다.** 검사 결과에도
"바가 5개뿐이라 초과분 없음 — 7번째 이후 검사 불가"로 남겼고 통과로 세지 않았다.
바가 7개 이상인 데이터가 생기면 그때 실측한다.

### ② 목표 트리 연쇄 — 값이 제자리에서 바뀌지 않으면 연쇄가 성립하지 않는다

연쇄를 붙이고 나서도 재생되지 않았다. 원인은 모션이 아니라 데이터였다 —
목표 화면이 `TASK_UPDATED` 를 듣지 않아 **업무 진척을 바꿔도 화면을 다시 열기 전까지
숫자가 그대로**였다. 제자리에서 오르는 것을 보여주는 모션인데 제자리 변화 자체가 없었다.

재생 조건은 셋을 **모두** 만족해야 한다.

| | 조건 | 안 그러면 |
| --- | --- | --- |
| ① | 사용자가 직접 값을 바꿨다 (`GOAL_CHAIN_EVENT`) | 남이 바꾼 값이 내 화면에서 혼자 굴러간다 |
| ② | 값이 실제로 바뀌었다 | 제목만 고쳐도 목표가 오른 것처럼 보인다 |
| ③ | 그 행이 지금 화면에 보인다 | 스크롤 아래에서 혼자 재생되고 끝난다 |

③ 에서 **나중에 보일 때도 재생하지 않는다.** 그때는 "방금 내가 한 일"이 아니다.

신호는 `TASK_UPDATED` 와 **다른 이벤트**를 쓴다. `TASK_UPDATED` 는 재조회에서도 뜨지만
`GOAL_CHAIN` 은 사람이 값을 움직인 자리에서만 쏜다. 그리고 진척에 영향을 주는 필드
(`progress`·`status`·`resolution`·`goalIds`·`goalSource`·`projectId`)일 때만 쏜다.

연달아 바꾸면 진행 중이던 연쇄의 타이머와 RAF 를 **끊고** 최신 값으로 다시 시작한다.
겹쳐 쌓이면 숫자가 두 방향으로 동시에 굴러간다.

## 쓰기 동작이 있는 검증 스크립트는 로컬에만 붙는다 (MD-P-2026-027 지시 32)

`scripts/local-only.mjs` 의 `requireLocalDb()` 를 **첫 줄에서** 부른다.
`DATABASE_URL` 의 호스트가 `127.0.0.1`·`localhost` 가 아니면 즉시 종료한다.
**우회 플래그를 만들지 않는다** — 우회로가 있으면 급할 때 반드시 쓰이고,
급할 때가 정확히 실수하는 때다. 파일 상단 주석에도 "로컬 전용. 원격 DB 에서 실행 금지"를 적는다.

이 잠금이 붙은 스크립트: `capture-empty-states` · `first-run-walk` · `init-db` ·
`md024-purge-demo` · `member-boundary` · `saved-view-walk` · `seed-demo` ·
`task-create-walk` · `goal-patch-fail-probe` · `motion-frames` · `verify-blob-access`.

**왜 생겼나.** §D3(다중 선택 일괄 지정) 검사가 목록의 앞 두 줄을 그냥 체크했고,
그 둘은 진짜 업무였다. 일괄 지정이 실제로 그 업무들의 프로젝트를 바꿨다.
로컬이라 되돌렸지만, 같은 스크립트가 프로덕션 DSN 을 물었다면 되돌릴 방법이 없었다.
"자기가 만든 행만 만진다"는 사고 **범위**를 줄이고, 이 잠금은 사고 **자체**를 막는다.
둘 다 필요하다. 접속 문자열은 오류 메시지에도 찍지 않는다 — 호스트만 보인다.

### 무한 반복을 걷어낼 때는 **뜻**을 남긴다

스피너·호흡·펄스·심박을 지우면서 상태의 의미(색·링)는 그대로 뒀다.
"작업 중"은 코랄 배경으로, "지금"은 오늘 선의 위치와 정지한 코랄 점으로 읽힌다.
움직임이 유일한 신호였던 곳은 없었다 — 있었다면 지우기 전에 대체 신호를 먼저 만들어야 한다.

### 접근성 차단은 이길 수 있어야 한다

`@media (prefers-reduced-motion: reduce)` 안의 전역 리셋은 `!important` 를 쓴다.
`*` 는 특이도 0 이라 `.agf-fab` 같은 클래스 규칙을 못 이긴다 —
`!important` 없이 썼더니 FAB 하나의 `transition: transform` 이 **21경로 전부에서 살아남았다.**
화면마다 예외를 하나씩 적는 방식은 반드시 빠뜨린다. 규칙을 전역으로 두고 이기게 한다.

### 검사가 낡은 규칙을 지키지 않게 한다

026 §A-4 는 "shimmer 금지"였고 빈 상태 검사가 "스켈레톤 애니메이션 0"을 단언했다.
027 §H2 가 스켈레톤 한 곳에 shimmer 를 허용하자 그 단언이 **정상 동작을 위반으로** 잡았다.
규격이 바뀌면 검사도 같이 바꾼다. 지금은 "sk-shimmer 뿐인가 · 아예 없지는 않은가 ·
reduce 에서 멈추는가" 셋을 본다.

그래서 세 가지를 바꿨다.

| | 전 | 후 |
| --- | --- | --- |
| 지정 방식 | 자유 경로 문자열 | **정해진 이름**(`EmptyIcon` 유니온) — 오타가 타입 오류가 된다 |

공용 선화 5종 — 화면마다 새로 만들지 않고 이 안에서 고른다.

    tasks     업무·목표 목록      (체크 목록)

## 폰트 6단과 행 높이 (§G · MD-P-2026-031 §A1 · §A2)

**하드코딩 `font-size` 를 쓰지 않는다.** 여섯 개 토큰 중 하나를 고른다.
값이 아니라 **자리**를 고르는 것이다. 단계를 늘리지 않는다.

| 토큰 | 값 | 쓰임 |
| --- | --- | --- |
| `--f1` | 26px | 화면 제목 |
| `--f2` | 20px | 카드/섹션 제목 · 큰 수치 |
| `--f3` | 15px | 강조 본문 |
| `--f4` | 13.5px | **본문 기본** · 목록 제목 |
| `--f5` | 12px | 보조 · 수치 |
| `--f6` | 11px | 라벨 · 메타 (**하한**) |

- **11px 미만 글자는 화면에 존재하지 않는다.** `--f6` 아래 단계는 만들지 않는다.
- 레거시 토큰(`--fs-*` · `--text-*` · `--num-kpi`)은 전부 위 여섯 단계로 접혀 있다.
  두 벌을 두면 다시 갈라진다.
- 검증은 **계산된 `font-size`** 로 한다. 소스를 grep 하면 상속·계산값을 놓친다.
  `scripts/align-walk.mjs` 가 21경로에서 글자를 직접 가진 요소를 전부 훑는다.

**행 높이.** 목록 행 `--row-h` **44px** / 그룹·섹션 헤더 `--hdr-h` **38px**.
밀도 완화가 아니라 담당자 이름과 상태 알약이 들어갈 자리다.

### 적용 범위 — 화면 UI 에만. 인쇄 미리보기는 인쇄 규격을 따른다
> **§A1 적용 범위.** 화면 UI 에만 적용한다. `--f6`(11px)이 하한이다.
> **인쇄 미리보기(`.prep-*` 계열)는 인쇄 규격을 따른다. 하한 7.5pt.**
> 이 예외는 `pt` 단위로 선언되고 인쇄 미리보기 컨테이너(`.prep`) 안에 있는 것에만
> 해당한다. px 로 선언된 것은 예외가 아니다.

`pt` 는 물리 크기이고 `px` 는 화면 크기다. **두 매체에 같은 하한을 걸면 안 된다.**
8pt 표는 종이에서 완전히 읽힌다 — 신문 본문이 9pt, 각주가 7~8pt 다. 억지로 올리면
표가 한 장을 넘길 위험이 생기고, 그건 규격 준수가 아니라 문서를 망가뜨리는 것이다.
(한 번 8.3pt 로 올렸다가 되돌렸다. 규칙이 매체를 구분 못 한 것이지 코드가 틀린 게 아니었다.)

**예외를 "검사 안 함"으로 두지 않는다.** `align-walk` 는 매체별 하한을 **둘 다 잰다** —
화면 11px, `.prep` 안 7.5pt. 그리고 `.prep` 안에서 11px 미만인 요소는 **자기에게 걸린
규칙이 실제로 `pt` 로 적혔는지** 되짚는다. 선택자 이름만 보고 봐주면 다음 사람이
`.prep` 안에 px 를 넣고 "예외"라고 부른다. (`.prep-lv` 를 `10px` 로 바꿔 넣어 검사가
7건을 잡는 것까지 확인했다 — 부재 단언에는 짝이 되는 존재 단언이 붙는다.)

### 줄어들지 않는 것들 — CSS 가 기본값으로 조용히 다르게 동작하는 자리
칸에 맞춰 줄어들 거라고 기대했는데 안 줄어드는 자리가 있다. 둘 다 §A 에서 실제로 잡혔다.

| 자리 | 왜 안 줄어드나 | 고치는 법 |
| --- | --- | --- |
| `flex` · `inline-flex` 의 자식 | `min-width` 기본이 `auto` 라 내용보다 작아지지 않는다 | `min-width: 0` |
| 인라인 요소(`<span>` 기본) | `max-width` · `width` 가 **적용되지 않는다** | `display: inline-block` |
| `table-layout: fixed` 의 칸 | CSS 의 `width` 가 `<col>` 을 못 이긴다 | 폭은 `colgroup` 에서만 정한다 |

세 번째는 특히 조용하다. CSS 만 고치고 "고쳤는데 안 바뀐다"며 헤매게 된다.

### 글자가 커지면 칸이 깨진다 — 같이 재야 한다
폰트를 한 단계 올리면 **고정 폭 칸에서 상자가 밀려 나간다.** 실제로 셋이 잡혔다.
체크박스가 34px 칸에서 잘려 말줄임표가 찍혔고(`…`가 체크박스 옆에 보였다),
"우선순위" 머리글이 68px 에 안 들어갔고, 구성원 이름 상자가 82px 밖으로 나갔다.

- 판정은 **자식 요소의 상자가 칸 밖으로 나갔는가**로 한다.
  글자가 말줄임표로 줄어드는 것은 의도이고, **상자가 잘리는 것은 결함**이다.
- 안 줄어드는 자리는 위 「줄어들지 않는 것들」 표를 본다.

## 검사 방식은 규칙이 정하지 않는다. 재려는 값이 정한다 (§G · MD-P-2026-031 §B2)

§B2 는 "정적 검사기를 만든다"고 적혀 있었다. `motion-audit` 이 정적이라 그대로 베낀 것인데,
모션은 **소스에 다 적혀 있어서** 정적으로 되는 것이고, 폭은 부모·형제·글자 길이가 같이
정하므로 **소스에 없다.** 재려는 값이 소스에 없으면 정적 검사는 원리적으로 불가능하다.

> **규칙.** 값이 소스에 적혀 있으면 정적으로, 화면이 계산해야 나오면 브라우저에서 잰다.
> 지시서가 방식을 지정했더라도 값이 그 방식으로 안 나오면 **방식을 바꾸고 보고한다.**

## 허용 목록은 만료된다 (§G · MD-P-2026-031 §B2)

예외를 파일로 남기는 것만으로는 부족하다. 고쳐진 뒤에도 목록에 남으면 **예외였던 것이
영구 면제로 굳고**, 목록이 현실과 갈라진다.

> **규칙.** 검사가 더 이상 걸지 않는 허용 항목은 통과가 아니라 **실패**다.
> 예외에 `until` 을 적을 수 있으면 적는다. 적을 수 없는 예외는 사유가 영구적이라는 뜻이고,
> 그 사유가 정말 영구적인지 다시 본다.

`density-audit` 에서 실제로 한 건(`cal2-bar.s-end`)이 이렇게 잡혀 지워졌다.

## 홈의 경계 — 업무의 상태와 사람의 행동을 섞지 않는다 (§G · MD-P-2026-031 §C)

같은 지연 업무가 판단 타일과 「나의 초점」 양쪽에 뜨면 **둘 다 안 읽힌다.**

| 자리 | 담는 것 | 예 |
| --- | --- | --- |
| §C1 판단 타일 | **업무의 상태** | 지연 · 이번 주 · 막힘 · 내가 막는 것 |
| 레일 「오늘의 활동」 | **사람의 행동** | 멘션 · 답글 · 승인 요청 · 남이 바꾼 것 |

**업무 상태는 레일에 넣지 않는다. 사람의 행동은 타일에 넣지 않는다.**

## 관측 도구부터 확인한다 (§G · MD-P-2026-031 §C)

「전체 기간을 눌러도 아무것도 안 바뀐다」를 코드 문제로 의심했다. 원인은 `npm run build`
가 `.next` 를 지워 **dev 서버 청크가 404** 였고, 페이지가 하이드레이션되지 않아 클릭이
죽어 있던 것이다.

> **규칙.** 화면이 반응하지 않으면 코드를 의심하기 전에 **화면이 살아 있는지** 확인한다.
> 콘솔 오류 · 네트워크 404 · 하이드레이션 실패를 먼저 본다.
> **관측 도구가 고장난 상태에서 잰 값은 값이 아니다.**
> 실측 보고에는 그 회차의 콘솔 오류 건수를 함께 적는다. **0건이 아니면 실측이 아니다.**

`align-walk` · `density-audit` · `deadline-walk` · `listquery-walk` 는 콘솔 오류가 하나라도 있으면
**측정 자체를 실패로 끝낸다.** (페이지를 떠나며 취소된 요청은 오류가 아니다 — `ABORTED` 는 뺀다.)

이 단언이 붙자마자 **B-15 중첩 button 이 하이드레이션 경고로 잡혔다.** 눈으로는 몇 달을
못 봤고 검사도 못 잡던 것이 콘솔 한 줄로 나왔다.

### 선택자를 짐작하지 않는다

`newuser-walk` 가 빈 상태를 `.es` 로 찾다가 못 찾고 **"빈 표만 있다 · FAIL"** 을 냈다.
화면은 멀쩡했다. 실제 클래스는 `.empty-state`(전체) / `.sec-empty`(섹션)이다.
관측 도구가 틀린 두 번째 사례다(첫 번째는 dev 서버 청크 404).

> **규칙.** 검사기가 찾는 **선택자 · 문구 · 경로는 화면에서 확인한 뒤 적는다.**
> 짐작한 선택자로 낸 FAIL 은 결함이 아니라 **검사의 오작동**이고,
> **그 상태로 코드를 고치면 멀쩡한 것을 망가뜨린다.**

두 사례의 공통점은 하나다 — **FAIL 을 보면 코드보다 검사를 먼저 의심할 이유가 있는가**를
묻는다. 「예외가 위반보다 많으면 검사기를 의심한다」의 작은 형제다.

## 묶음의 대표값은 묶음 전체가 같을 때만 쓴다 (§G · MD-P-2026-031 §C2)

「프로젝트 없음」 그룹 머리줄이 영역을 **「R&D」**라고 적고 있었다. 그 묶음에는
R&D · 디자인 · 플랫폼 · 기타가 섞여 있었고, 코드는 첫 행의 영역을 쓰고 있었다.
**틀린 값이 아니라 틀린 요약이라 더 나쁘다** — 사람이 그 줄을 믿는다.

> **규칙.** 첫 행 · 최빈값 · 최댓값으로 묶음을 대표하지 않는다. 섞여 있으면 **적지 않는다.**
> 적지 않는 것이 정보 손실로 보이면, 그건 그 자리에 요약이 아니라 **개수**가 와야
> 한다는 뜻이다 (`영역 4종` 처럼).

## 기한 막대 목록의 눈금 범위 — stub 비율이 판정한다 (§G · MD-P-2026-031 §C2)

눈금을 한 달로 고정했더니 **36행 중 24행에 막대가 없었다**(구간 밖 16 · 기한 없음 8).
기한 막대 목록인데 3분의 2가 막대가 아니다. 이건 구현 결함이 아니라 **범위가 틀렸다는
신호**다. 지연이 많은 데이터에서는 왼쪽 밖 화살표가 줄줄이 서고, 그건 정보가 아니라 소음이다.

> **규칙. stub 비율 ≤ 20%.**
> 표시 행 중 구간 밖이라 막대를 못 그린 행이 20% 를 넘으면 **눈금 범위가 틀린 것**으로 본다.
> **기한 없음은 분모에서 뺀다** — 그건 데이터가 없는 것이지 범위 문제가 아니다.
> 판정식은 `lib/task-bars.ts` 의 `stubRatio()` 하나뿐이다.

범위는 **새 컨트롤을 만들지 않고** 화면에 이미 있는 기간 토글에 연결한다.
`이번 분기`(기본) = 그 분기 3개월, 눈금은 월 경계. `전체 기간` = 대상의 min~max + 5% 여백.
**어느 쪽이든 오늘이 범위 밖이면 그 범위를 쓰지 않는다** — 오늘 선이 없는 시간축은
읽을 기준이 없다.

    한 달 고정   막대 12 · 구간 밖 16      → 57%   범위가 틀렸다
    이번 분기    막대 28 · 구간 밖  0      →  0%
    전체 기간    막대 28 · 구간 밖  0      →  0%

## 캡처를 근거로 결함을 주장할 때 (§G · MD-P-2026-031 §C 중간 병합)

프로젝트 상세 「최근 활동」에 `진행률 변경 (0% → 90%)` 이 다섯 줄이었고, 목록의 그 업무는 0% 였다.
**"저장이 안 된다"로 읽혔다. 틀렸다.** 같은 그림을 설명하는 가설이 둘이었기 때문이다 —
저장이 안 된다, 그리고 **매번 되돌려졌다.** 뒤엣것이 정답이었다(검사기가 SQL 로 복구했다).
게다가 그 캡처는 프로덕션이 아니라 **로컬**이었다.

> **규칙.** 캡처를 근거로 결함을 주장할 때는 두 가지를 먼저 적는다.
> **① 어느 환경인가**(로컬 / 프로덕션) · **② 이 그림을 설명하는 가설이 몇 개인가.**
> 가설이 둘 이상이면 결함이라고 부르지 않는다. **구분할 관측을 먼저 지정한다.**
> 이번의 그 관측은 "되돌리는 경로가 있는가" 였고, **5초 간격**이 답이었다.

### 사람의 흔적인지 기계의 흔적인지는 **간격**이 말한다

`진행률 변경` 마다 정확히 5~6초 뒤에 같은 `목표 수정`. 열 번 전부. 사람의 간격이 아니다.

> **규칙.** 로그를 읽을 때 **내용보다 시각 간격을 먼저 본다.**
> 규칙적인 간격 · 초 단위로 같은 차이 · 자정 직후 몰림은 사람이 아니다. **사람은 불규칙하다.**

## 검사가 남긴 흔적은 값 · 기록 · 파생물 셋 다 되돌린다 (§G · MD-P-2026-031 §C)

검사가 진행률을 바꿔 재고 `finally` 에서 SQL 로 되돌렸다. 값은 정확히 복구됐다.
그런데 **되돌림은 로그를 안 남기므로** 화면에는 "90 으로 올렸다"만 열 줄 쌓였고,
그 열 줄이 **PM 의 오진을 만들었다.** 값만 복구하고 기록을 두면 그 기록이 다음 사람의 판단 재료가 된다.

> **규칙.** 검사가 남긴 흔적은 **값 · 기록 · 파생물** 셋 다 되돌린다.
> 활동 로그 · 알림 · 캐시 · 집계 스냅샷이 그 대상이다.
> **몇 건을 지웠는지 찍는다.** 조용히 지우면 안 지운 것과 같다.

지우는 방법도 손 목록으로 두지 않는다. `actor(id)` 를 참조하는 곳은 **39군데**이고,
손으로 적은 목록에서 `read_marker` 하나가 빠져 있어 정리가 죽었다. 정리가 죽으니
**계정이 매 회차 하나씩 쌓였다.** 지금은 `scripts/purge-actor.mjs` 가 **스키마에 물어보고** 지운다.

### 찌꺼기 덕분에 통과하는 검사가 있다

정리를 고쳐 DB 가 깨끗해지자 `first-run-walk` 의 한 단계가 시간초과하기 시작했다.
**이전 회차가 남긴 찌꺼기가 있을 때만 통과하고 있었던 것이다.**

> **규칙.** 검사는 **깨끗한 상태에서** 통과해야 한다.
> 정리를 고쳤을 때 없던 실패가 생기면, 그것은 새 결함이 아니라 **가려져 있던 실패**다.

### 오래 돌린 dev 서버에서 잰 값도 값이 아니다

검사 수십 회를 연달아 돌린 뒤 `listquery-walk` 이 회차마다 **다른 항목**을 실패했다.
실패 모양이 전부 같았다 — 주소가 정정되지 않았고, 값이 확정 전이었다. **시간 모양**이다.
dev 서버를 재시작하니 3회 연속 20/20.

> **규칙.** 회차마다 **다른 항목**이 실패하고 그 모양이 전부 시간 관련이면,
> 코드가 아니라 **재는 환경**을 먼저 의심한다. dev 서버는 오래 돌리면 느려진다.
> 「관측 도구부터 확인한다」의 확장이다 — 도구는 고장 나기도 하지만 **늙기도 한다.**

## 검사기를 검사한다 — `scripts/checker-audit.mjs` (§G · MD-P-2026-031 §C)

「검사도 낡는다」가 **세 번** 났다 — `subtask-walk` 의 `=== 38`, `goal-link-walk` 의 `.lmn`,
`goal-screen-walk` 의 `"19px"` · `"12.5px"`. 세 번이면 개별 수정으로 끝낼 일이 아니다.

전수 조사에서 나온 것 (전 36개 스크립트).

| 대상 | 건수 | 처분 |
| --- | --- | --- |
| `.frn-x` (실제 `.frn-skip`) | 5 | 고침 — 첫 실행 안내를 **한 번도 닫지 못하고 있었다** |
| `.pg-actions` (실제 `.pg-act`) | 1 | 고침 — 늘 0 을 세어 **조용히 통과**하고 있었다 |
| `.lmn` (지운 컴포넌트) | 2 | 의도된 **부재 단언** — `audit:absent` 로 선언 |
| 죽은 갈래(`.tv-quick` · `.propb`) | 2 | 하나는 제거, 하나는 원인 규명 전까지 선언 후 보류 |
| 박아 둔 규격 숫자 | 0 | 토큰 대조로 이미 전환 |

> **규칙 ①. 없는 선택자를 세는 단언은 「조용히 통과한다」 — 틀린 FAIL 보다 나쁘다.**
> 틀린 FAIL 은 최소한 보인다. 조용한 통과는 아무도 모른다.
> **규칙 ②. 규격값은 토큰에서 읽어 대조한다.** 값이 아니라 **이름**이 규격이다.
> **규칙 ③. 없는 것이 정상인 선택자는 `audit:absent` 로 선언한다.** 적지 않으면 낡은 것으로 본다.

### 0 을 기대하는 단언에는 **짝을 붙인다**

`.pg-actions`(실제 `.pg-act`)가 늘 0 을 세면서 「헤더에 코랄이 없다」를 **영원히 통과**시켰다.

> **규칙. 없는 것을 세는 단언은 통과가 아니라 미검사다.**
> 0 을 기대하는 단언에는 **0 이 아닌 경우를 만들어 한 번 실패시키는 짝**을 붙인다.
> 짝을 못 만들면 그 단언은 아무것도 지키지 않는다.

### 검사에서 **예외를 삼키지 않는다**

`.catch(() => {})` 때문에 다섯 검사기가 첫 실행 안내를 **한 번도 못 닫은 채** 돌았다.
오타(`.frn-x`)가 몇 달을 살아남은 이유가 이것이다.

> **규칙. `catch` 로 빈 블록을 쓰지 않는다.**
> 실패해도 되는 동작이면 **"실패해도 된다"를 로그로 남긴다.**
> 조용히 넘어가는 실패는 **없는 실패**가 되고, 그 위에서 잰 값은 전부 의심스러워진다.

`checker-audit` 이 남은 것을 센다(현재 28건). 판정에는 아직 안 넣었다 —
**한 번에 다 고치면 그 자체가 위험하다.** 실제로 일괄 치환을 시도했다가 12곳 중 7곳에
엉뚱한 문구가 들어갔고 되돌렸다. §D 에서 줄인다.

### 연쇄 삭제 대상은 **스키마에 물어본다**

`actor(id)` 참조 39군데를 손 목록으로 관리하다 `read_marker` 가 빠져 정리가 죽었다.

> **규칙. 연쇄 삭제·정리 대상은 스키마에 물어본다. 목록을 코드에 적지 않는다.**
> 이것은 「검사도 낡는다」의 **데이터 쪽 형제**다.


### 빈 것끼리 같은 것은 **같은 것이 아니다**

`.frn-x` 수정 전후를 대조하는데 검사기 셋의 결과 해시가 전부 `d41d8cd98f00` 으로 같았다.
**빈 문자열의 해시**였다 — dev 서버가 죽어 있었고, 빈 출력끼리 일치했다. "동일"로 읽을 뻔했다.

> **규칙. 대조는 「같은가」 전에 「비어 있지 않은가」를 먼저 단언한다.**
> 결과줄 0 · 빈 출력 · 빈 배열은 일치가 아니라 **미측정**이다.
> 이것은 「두 도구가 같은 값을 냈다는 것은 정확성의 증거가 아니다」의 극단이다 —
> **둘 다 아무 말도 안 한 것을 합의로 읽으면 안 된다.**

`checker-audit` 은 이 규칙을 **자기 자신에게** 건다(④ 절). 훑은 스크립트 수 · 대조할
코드베이스 크기를 단언하고, **일부러 틀린 표본을 물려 세 탐지기가 각각 반응하는지** 본다.
자기 점검이 깨지면 나머지 0건은 증거가 아니므로 **판정 자체를 실패로** 끝낸다.

### 한 번에 다 고치는 것이 **그 자체로 위험하다**

빈 `catch` 12곳을 일괄 치환했더니 **7곳에 엉뚱한 문구**가 들어갔다
(「첫 실행 안내 없음」이 영역 칩 클릭·모달 열기 자리에 붙었다). 되돌리고 5곳만 고쳤다.

> **규칙. 일괄 수정은 「같은 모양」이 아니라 「같은 뜻」일 때만 한다.**
> 모양이 같아도 자리마다 뜻이 다르면 일괄이 아니라 **개별**이다.
> 일괄로 가려면 **배치를 나누고 배치마다 검증**한다. 한 배치가 틀리면 그 배치만 되돌린다.
> **되돌릴 수 없는 크기로 고치지 않는다.**

#### §D 진행 방식 — 이 규칙이 정한다

§D 는 본체가 대량 일괄 수정이다(버튼 179개 배정 · 칩 14종→5종 · 세로 정렬 잔여 ·
조상 선택자 전수 · 빈 `catch` 28건).

> **한 종류를 한 커밋에, 한 커밋을 20~30건 배치로 나눈다.**
> 배치마다 회귀를 돌리고 **배치 번호와 건수를 보고에 남긴다.**
> "179개를 전부 배정했다"는 한 줄로 끝내지 않는다 —
> **되돌려야 할 때 어디까지 되돌리면 되는지가 보고에 있어야 한다.**

빈 `catch` 28건은 `checker-audit` 이 세되 **판정에는 안 넣는다.**
넣는 것은 **0 이 된 뒤**다 — 28인 채로 판정에 넣으면 매 회차 빨간 줄만 보게 되고,
빨간 줄이 늘 있으면 아무도 안 본다.


## 눈금 범위는 컴포넌트의 기본값이다 (§G · MD-P-2026-031 §C 중간 병합)

홈의 stub 을 57% → 0% 로 고쳤다. 그런데 **같은 병이 `/tasks` 에 그대로 남아 있었다** —
이번 달 고정이라 6행 중 3행이 구간 밖(**50%**)이었고, 병합 직전 캡처를 보고서야 드러났다.
화면마다 범위를 고르게 두었으니 화면마다 다르게 났던 것이다. §C3·§D 에서 화면이 늘면 또 갈린다.

> **규칙.** **눈금 범위는 컴포넌트가 정한다**(`defaultBarRange`).
> 화면은 "막대를 켠다"만 말하고(`timelineToday`), 범위는 안 고른다.
> **덮어쓰려면 이유를 주석으로 적는다**(`timeline`).

지금 덮어쓰는 곳은 하나다 — 홈. 「이번 분기 / 전체 기간」 토글이 있고,
**그 토글이 곧 사용자가 고른 범위라서 컴포넌트 기본값보다 세다.** 이유가 그것이다.

같은 형태의 규칙이 이미 여럿 있다 — 진척은 `lib/progress.ts`, 기한 급함은 `lib/task-view.ts`,
막대 좌표는 `lib/task-bars.ts`, 영역 분류는 `lib/area-policy.ts`, 초기값은 `lib/use-list-query.ts`.
**여러 화면이 같은 것을 그리면, 그 값의 출처는 하나여야 한다.** 화면은 켜고 끌 뿐이다.

## 숫자만 있고 분모가 없는 진척은 화면에 두지 않는다 (§G · MD-P-2026-031 §C 중간 병합)

같은 프로젝트(EDUINO AI)가 두 화면에서 이렇게 보였다.

| 화면 | 값 | 분모 |
| --- | --- | --- |
| 프로젝트 상세 「진척 롤업」 | **38%** | 업무 26건 (완료 포함) |
| 홈 목록 그룹 머리줄 | **11%** | 업무 18건 (열린 것만) |

030 에서 진척 계산기 아홉 갈래를 하나로 합쳤다. **이번에 갈린 것은 계산기가 아니라 분모다.**
같은 함수에 다른 집합을 넣으면 다른 값이 나온다 — 완료가 100 으로 들어가니 38 이 된다.
**두 숫자를 나란히 본 사람은 어느 쪽도 믿지 않는다.**

> **규칙.** 집계 퍼센트는 **분모를 함께 적는다** — `11% · 업무 18건 기준`.
> 형식은 화면마다 같게 한다. **숫자만 있는 진척은 화면에 두지 않는다.**

「진행 중 N건 기준」이라고 쓰지 않는다 — 완료 포함을 켜면 거짓이 된다.
**어느 쪽이 옳은지는 아직 안 정했다**(§C4). 지금은 "다른 것을 재고 있다"를
화면이 말하게만 한다. §C4 에서 답할 질문은 이것이다 —
**그룹 롤업은 「진행 중인 것들이 얼마나 됐나」인가, 「이 프로젝트가 얼마나 됐나」인가.**

## 이미 찍힌 화면에 답이 있으면 다시 재지 않는다 (§G · MD-P-2026-031 §C)

홈 타임라인이 「업무 33」인데 활성이 41건이라 8건의 행방을 물었다. 답은 **이미 찍혀
있었다** — 같은 회차의 `/tasks` 캡처 우하단에 `31건 · 완료 8건 숨김`.

> **규칙.** 캡처 · 로그 · 기존 보고에 있는 값을 새로 조회하는 것은 검증이 아니라 중복이다.
> 단 **어느 캡처의 어느 자리에서 읽었는지**를 적는다. 기억에서 꺼내면 그건 추측이다.

## 중간 상태도 상태다 (§G · MD-P-2026-031 §C)

정렬이 서버로 넘어가자 요청이 **두 번** 나갔다. 초기값(주소·저장값)을 읽기 전에 한 번
부르기 때문이다. 최종 화면은 맞았지만 그 사이에 **틀린 순서가 화면에 보였다.**
드래그 정렬 검사가 그 짧은 순간을 잡았다.

> **규칙.** 최종 화면이 맞다는 것은 통과 조건이 아니다.
> 로딩 → 첫 렌더 → 확정 사이에 **틀린 값이 한 프레임이라도 보이면 결함**이다.
> 초기값(주소 · 저장값 · 사용자 설정)을 읽기 전에는 요청하지 않는다.
> 읽는 동안은 스켈레톤이다. **기본값으로 한 번 그리고 고쳐 그리지 않는다.**

### 세 번째가 나기 전에 구조로 막는다 — `useListQuery()`

같은 결함이 **두 번** 났고, 두 번 다 **초기값이 하나 늘어난 순간**이었다.
정렬이 늘었을 때, 영역이 늘었을 때. 고칠 때마다 컴포넌트에 조건문이 하나씩 붙었고
(`inited` · `areaDefaulted`), 파라미터가 늘 때마다 네 화면에 같은 조건문이 흩어질 참이었다.

> **규칙.** 목록 화면의 초기값은 **`lib/use-list-query.ts` 하나가 읽는다.**
> 주소 · localStorage · 기본값 · 옛 값 매핑 · 주소 정정이 전부 이 훅 안에 있다.
> 부르는 쪽은 `ready` 하나만 본다. 파라미터가 늘어도 부르는 쪽 코드는 안 바뀐다.

| 규약 | 뜻 |
| --- | --- |
| 주소 > 저장값 > 기본값 | **공유 링크가 이긴다.** 저장값은 주소가 없을 때만 산다 |
| `ready:false` 동안 안 부른다 | 다 정해지기 전에 부르면 기본값으로 받고 다시 받는다 |
| 기본값은 주소에 안 쓴다 | 바뀐 것만 남는다. `replaceState` — history 를 안 쌓는다 |
| 모르는 값은 400 이 아니다 | 기본값으로 떨어뜨리고 **주소를 정정한다** |
| 이름만 바뀐 값은 조용히, 없어진 값은 한 번 말한다 | `recent→created` 는 침묵, `progress→due` 는 안내 1회 |

검사는 `scripts/listquery-walk.mjs` 다. 화면을 보는 것이 아니라 **나간 요청의 수**를 센다 —
"최종 화면이 맞다"로는 이 결함이 안 잡히기 때문이다.

#### 클라이언트 컴포넌트라도 **첫 HTML 은 서버가 그린다**

훅을 붙이고 검사를 세 번 돌렸더니 세 번째에서 실패했다. `/?span=all` 인데 「이번 분기」 칩이
켜져 있었다. 마운트 이펙트에서만 주소를 읽으니 **하이드레이션이 끝날 때까지** 기본값이
나간 것이다. 한 프레임이 아니었다. `/tasks?sort=priority` 는 서버 HTML 에
`<option value="due" selected>` 가 아예 박혀 나왔다.

> **규칙.** 서버가 답을 아는 값은 **첫 바이트부터 맞아야 한다.**
> 서버가 아는 키는 둘이다 — ⓐ 주소에 값이 있는 키(주소가 저장값을 이기므로 답이 정해진다),
> ⓑ 저장값을 안 보는 키(주소에 없으면 기본값이 답이다).
> 페이지(서버 컴포넌트)가 `searchParams` 를 훅에 넘기고, 훅은 그 값으로 **첫 렌더를 시작한다.**
> 서버와 클라이언트가 **같은 정규화 함수**를 쓴다 — 두 벌로 쓰면 하이드레이션이 갈라진다.

남는 한 가지: **주소에 없고 저장값에서 오는 값**은 서버가 알 수 없다(localStorage 는 서버에 없다).
그 키가 하나라도 있으면 `ready` 는 거짓으로 시작하고 — **그래서 목록을 안 부른다.**
컨트롤 라벨만 잠깐 기본값이고, 데이터는 틀린 상태로 그려지지 않는다.

검사는 브라우저로 재지 않고 **서버가 준 HTML 문자열을 직접 읽는다.** 브라우저로 재면
"언제 재느냐"에 답이 달라져 검사가 흔들린다 — 실제로 400ms 뒤에 재서 두 번 통과하고 한 번 실패했다.
**흔들리는 검사는 통과한 회차도 증거가 아니다.**

#### 한 파라미터를 두 곳에서 쓰지 않는다

훅이 주소를 쓰기 시작했는데 컴포넌트의 옛 쓰기 이펙트도 같은 키를 계속 쓰고 있으면,
**둘 중 어느 쪽이 마지막이었는지에 따라 주소가 달라진다.** 같은 화면이 같은 조작에
다른 주소를 낸다. 훅으로 옮긴 파라미터는 옛 이펙트에서 **그 자리에서 지운다.**

#### 기본값이 「사용자의 속성」이면 사용자 정보가 나오는 자리에서 낸다

담당 기본값(본인)과 영역 기본값(내 영역)을 화면이 `/api/meta/selectors` 응답을 기다려
알아내고 있었다. 그래서 "정해졌는가"를 세는 게이트(`areaDefaulted`)가 필요했고,
§C3·§C4 로 화면이 넷이 되면 그 게이트가 **네 곳으로 복제될** 참이었다.

> **규칙.** 기본값이 사용자의 속성이면 **서버가 사용자 정보와 함께 낸다**(`lib/user-defaults.ts`).
> 그 자리는 **「기본값」만 낸다. 「선택지 목록」은 안 낸다** — 목록은 계속
> `/api/meta/selectors` 가 답한다. 둘을 합치면 모든 페이지가 목록 전체를 지고 다니고,
> 목록이 바뀔 때마다 값이 낡는다.

**쿠키(세션 토큰)에 굽지 않는다.** 이미 로그인해 있는 사람의 토큰에는 그 값이 없어
세션 수명(7일) 동안 서버가 답을 모르고, 그 경우를 받으려면 **방금 없앤 게이트를 다시
남겨야 한다.** 매 요청 읽으면 낡지도 않는다 — `actor_area` 는 사람당 한두 행이다.

「지금 이 화면을 넓게 열 것인가」(홈 판단 타일에서 온 진입이면 전체 영역·전체 담당) 같은
**진입 판단도 서버에서 한다.** 예전에는 마운트 이펙트가 주소를 다시 읽어 담당을 넓혔고,
그래서 첫 렌더는 내 담당, 확정 렌더는 전체 담당이었다.

## 검사는 화면이 실제로 보는 것을 봐야 한다 (§G · MD-P-2026-031 H-2)

`hotfix-walk` 이 임박 등급을 만들려고 `id` 순 앞 두 건의 기한을 바꿨다. 그런데 그 둘은
`/tasks` 의 기본 필터(내 영역 · 내 담당) **밖**이었다. 화면에는 안 나타났고 검사는
"임박이 없다"를 냈다. 그건 **색이 틀린 것이 아니라 검사가 대상을 못 본 것**이다.
둘은 결과가 같아서 구별되지 않는다.

> **규칙.** 검사가 만든 데이터는 검사가 보는 화면에 **실제로 나타나야 한다.**
> 필터 · 권한 · 페이지가 걸린 화면에서는 **먼저 조건을 연 뒤** 잰다.
> 만든 것이 안 보이는 상태로 "없다"를 재면, 그 검사는 자기가 만든 것도 못 찾는다.

(「밟히지 않은 분기는 통과가 아니라 미검사다」의 확장이다. 분기를 만들었어도 화면이
그 분기를 안 보면 여전히 미검사다.)

### 가려진 것은 「없는 것」이 아니다 — 세기 전에 먼저 연다

§C1 검사가 판단 타일의 「지연 27」과 목록의 코랄 행 수를 대조했다. 목록은 **24** 였다.
계산기가 갈린 줄 알았지만 아니었다 — 상시 업무 섹션이 **접혀 있었고**, 그 안의 3건을
검사가 못 셌다. 접힌 것을 세지 않은 것을 "없다"로 읽은 것이다.

> **규칙.** 접힘 · 탭 · 페이지 · 가상 스크롤로 가려진 것은 **「없는 것」이 아니다.**
> 세는 검사는 **세기 전에 먼저 연다.** 접힌 섹션을 펼치고, 탭을 돌고, 끝까지 스크롤한 뒤 센다.
> 열지 않고 잰 수는 화면에 지금 보이는 수일 뿐, 그 화면이 담고 있는 수가 아니다.

## 검사는 시점에 답이 달라지면 안 된다 (§G · MD-P-2026-031 §C 회신 5)

`listquery-walk` 가 두 번 흔들렸다.

- 고정 시간(`waitForTimeout(700)`)만 기다리고 요청 수를 셌더니, **늦게 나간 첫 요청**을
  "0회"로 읽었다. 통과가 아니라 미측정이다.
- 홈 기간 칩을 브라우저로 400ms 뒤에 쟀더니 **두 번 통과하고 한 번 실패**했다.
  칩이 틀린 게 아니라 잴 때마다 답이 달랐다.

> **§G. 검사는 시점에 답이 달라지면 안 된다.**
> 고정 대기(`sleep`)로 사건을 기다리지 않는다. **사건을 기다린 뒤 거기서부터 센다.**
> 시점에 따라 답이 달라지는 검사는, **통과한 회차도 증거가 아니다.**
> 서버가 만든 것은 서버 응답에서 재고, 브라우저가 만든 것은 브라우저에서 잰다 —
> **재려는 값이 만들어지는 자리에서 잰다.**

### 화면이 아니라 나간 요청의 수를 센다

「최종 화면이 맞다」로는 안 잡히는 결함이 있다. 이번에 두 번 증명됐다 —
요청이 두 번 나가 그 사이에 틀린 순서가 보인 것, 그리고 하이드레이션 전까지 기본값이
보인 것. 둘 다 마지막 화면은 옳았다.

> **규칙.** "무엇이 보이는가"로 못 잡는 것은 **"무엇이 일어났는가"로 잡는다.**
> 나간 요청의 수와 그 쿼리, 서버가 준 HTML 문자열, 콘솔 오류 건수가 그 재료다.

## 「값이 없음」은 「보여줄 것이 없음」이 아니다 (§G · MD-P-2026-031 §C 회신 6)

「새 계정 발급」 폼에 영역 칸이 없어서, 발급되는 계정은 `actor_area` 가 **0행**이다.
그 위에 "영역 기본값 = 내 영역"을 얹으면, 다음에 들어오는 사람의 **첫 화면이 빈 목록**이 된다.

> **규칙.** 사용자 속성이 비어 있을 때의 기본값은 **넓은 쪽**이다.
> 「소속이 없다」는 "볼 것이 없다"가 아니라 **"아직 안 정했다"**는 뜻이다.
> 아무것도 안 보이는 화면보다 다 보이는 화면이 낫다 —
> **안 보이면 없는 것이 되고, 그건 되돌리기 어렵다.**
> (§C1 「미분류 영역은 메인으로」와 같은 판단이고, 이유도 같다.)

폴백은 **값을 내는 자리 한 곳**에 둔다(`lib/user-defaults.ts`). 화면 쪽에 분기를 만들면
화면이 넷이 될 때 넷이 달라진다. 화면은 **이미 결정된 값**을 받는다.

### 기본값을 조건부로 만들지 말고, **넓히는 버튼**을 준다

신규 사용자의 `/tasks` 가 0건이었다. 원인은 영역이 아니라 **「담당 = 본인」** 이었다.
"담당 업무가 0건이면 전체 담당으로" 같은 폴백은 **기각한다** —
기본값이 데이터에 따라 달라지면 그것은 기본값이 아니라 **계산값**이고,
계산은 시점이 있으므로 `ready` 게이트가 훅 안으로 돌아온다.

> **규칙.** 기본값은 **정적으로 둔다.** 좁은 기본값 때문에 화면이 비면,
> **빈 상태가 넓히는 버튼을 준다.** 사용자가 한 번 눌러서 넓히고, 그 선택은 주소에 남는다.
> **기본값을 조건부로 만드는 것과 버튼 하나를 주는 것은 완전히 다른 일이다.**

### 빈 상태는 하나가 아니다 — 비는 이유마다 다음 행동이 다르다

「상단 필터를 조정하세요」 한 문장은 **어느 필터를 어떻게 하라는 말인지 안 알려준다.**

| 갈래 | 조건 | 문구 · 행동 |
| --- | --- | --- |
| ① 기본값만 좁혔다 | 담당=본인, 능동 조건 없음 | `아직 나에게 배정된 업무가 없어요` · **[전체 담당으로 보기]** |
| ② 좁힌 것이 없다 | 담당=전체, 조건 없음 | `아직 업무가 없어요` · `첫 업무를 만들어 시작하세요` |
| ③ 조건이 걸렸다 | 검색어·상태·기한·프로젝트·막힘·남의 담당·영역 | `조건에 맞는 업무가 없어요` · **걸린 조건을 그대로 나열** · **[조건 지우기]** |

갈래는 **지금 걸린 필터만 보고** 정한다. 팀 전체 건수를 세지 않는다 —
**숫자 하나 때문에 쿼리를 늘리지 않는다.** 그래서 ②는 "정말 아무 조건도 없는데 0건" 일
때만 쓴다. **그때만 참이라고 말할 수 있기 때문이다.**

「조건 지우기」는 **전부** 푼다. 하나만 풀면 또 0건일 수 있고, 그러면 같은 화면을 두 번 만난다.
행동은 둘까지다(넓히거나 지우는 버튼 + 만들기). **채움(코랄)은 그중 하나뿐이다**(§E1).

**알려진 경우 하나 — 고치지 않는다.** 워크스페이스가 통째로 비어 있으면 ①이 뜨고,
「전체 담당으로 보기」를 눌러 ②를 만난다. 같은 자리를 두 번 보는 셈이다.
**완전히 빈 워크스페이스에서만 나고, 두 번째 화면이 올바른 답(＋ 새 업무)을 주므로 둔다.**
(적어 두지 않으면 나중에 이걸 결함으로 보고 ①의 조건을 건드리게 된다. ①은
"팀 전체에 몇 건 있는가"를 **모르는 채로** 판정하도록 일부러 만든 것이다 — 그걸 알려면
쿼리를 하나 늘려야 한다.)

### 신규 사용자의 첫 화면은 **계정을 만들어서** 잰다

이 문제는 기존 계정으로는 절대 안 보인다. 셋 다 영역이 2개씩 있기 때문이다.
`scripts/newuser-walk.mjs` 는 **진짜 발급 API 를 불러** 계정을 만들고, 그 사람으로
로그인해 첫 화면을 잰 뒤 지운다. 발급을 흉내내면 **진짜 경로가 뭘 빠뜨렸는지가
영원히 안 보인다** — `actor_area` 를 안 만든다는 사실이 바로 그것이었다.

#### 첫 화면에는 **단계가 있다** — 어느 단계를 재는지 명시한다

> **규칙.** 비밀번호 벽 · 온보딩 안내 · 빈 상태는 **각각 다른 화면이다.**
> "첫 화면을 잰다"고 할 때 **어느 단계를 재는지 명시한다.**

이 규칙은 값을 치르고 얻었다. 처음에 단계를 **둘**로 보고(비밀번호 벽 → 목록)
"신규 사용자가 처음 보는 것은 빈 상태 문구"라고 보고했다. **틀렸다.**
사이에 **첫 실행 안내(`FirstRun`)** 가 있고 그것이 목록을 덮는다.

못 본 이유가 중요하다. DOM 만 읽었기 때문이다 — 빈 상태는 안내 **아래에** 멀쩡히 있었고
`innerText` 로는 읽혔다. 검사에 **클릭**을 넣자 대화상자가 클릭을 가로채면서 드러났다.

> **덮인 것이 없는 것이 아니듯, 읽히는 것이 보이는 것도 아니다.**
> 「접힌 것을 펼치고 잰다」의 반대 방향이다 — 저쪽은 안 그려진 것을 세는 실수이고,
> 이쪽은 **그려졌지만 가려진 것**을 보인다고 세는 실수다.

#### 방법 — **보인다는 것은 눌린다는 것이다**

> **규칙.** 요소가 보이는지 확인할 때 `innerText` · `display` · `visibility` 로 판정하지 않는다.
> **클릭이 그 요소에 닿는지**로 판정한다(`elementFromPoint` 또는 실제 클릭).
> 대화상자 · 오버레이 · `pointer-events` 는 **DOM 을 지우지 않고 가린다.**
> 이번 결함이 클릭을 넣은 순간에만 드러난 것이 그 증거다.

`align-walk` · `newuser-walk` 의 가시성 판정을 이 방식으로 통일한다 — **§D 착수 때.**

지금 `newuser-walk` 는 세 단계를 순서대로 잰다 —
**비밀번호 벽 → 첫 실행 안내 → 목록(빈 상태 세 갈래).**

## 규격 스타일은 조상 선택자에 매달지 않는다 (§G · MD-P-2026-031 §C1)

`.due` 는 기한 색 규격이다. 그런데 정의가 `.hv .due` 로 돼 있었다.
§C2 에서 새 목록이 `.hv` **밖**에 놓이자, 같은 클래스를 단 지연 27건이 전부 회색으로 떴다.
타일은 코랄 27, 목록은 코랄 0. 클래스는 맞게 붙어 있었고 **규칙이 안 닿았을 뿐**이다.

같은 사고가 이번이 **두 번째**다(첫 번째는 인쇄 미리보기의 폰트 하한).
클래스를 옮겨 붙이는 것은 자유롭고, 그 자유가 조상 선택자와 정면으로 부딪힌다.

> **규칙.** 규격 클래스(`.due` · `.st` · `.pjdot` · `btn-*` · 상태 칩 …)는
> **자기 이름만으로 완성돼야 한다.** 조상 선택자로 범위를 좁히지 않는다.
> 조상이 필요한 것은 **레이아웃**뿐이다 — 색 · 굵기 · 크기 같은 규격은 조상이 없어도 같아야 한다.
> 어느 컨테이너 안에 있느냐로 규격이 달라지면, 그것은 규격이 아니라 그 화면의 지역 규칙이다.

조사 대상 전수 목록은 §D 착수 시 만든다 — §E1 버튼과 §D2 상태 칩도 같은 대상이다.

## 표시 문자열로 정렬·비교하지 않는다 (§G · MD-P-2026-031 §C1)

판단 타일의 "가장 오래된 지연"이 `D+9` 로 떴다. 목록에는 `D+33` 이 있었다.
`dday` 문자열을 그대로 정렬해서 `"D+9" > "D+33"` 이 나온 것이다.

> **규칙.** 표시용 문자열(`D+9` · `2026.08.10` · `85%` · `1,204`)은 **보여주기 위한 것**이다.
> 정렬 · 비교 · 집계는 **그 문자열을 만든 원래 값**으로 한다.
> 원래 값이 화면 쪽에 없으면 서버가 같이 내려주거나, 문자열에서 숫자를 **파싱해서** 쓴다.
> 「사람이 읽는 값」과 「기계가 재는 값」은 같은 자리에 두지 않는다.

## 빈 가로 공간 금지 (§G · MD-P-2026-031 §B)

> **전체 폭을 쓰는 행은, 그 폭을 정보로 채우거나 폭을 줄인다.**
> 오른쪽 25% 이상이 빈 채로 남는 전체 폭 행은 규격 위반이다.
> 억지 여백(양 끝에 **두 개만** 두고 가운데를 비우는 것)도 위반이다.

### 무엇에 대해 25% 인가 — **content box(안쪽) 기준**
`padding` 은 의도된 여백이고, §B1 이 잡으려는 것은 **채우지 못한 폭**이다.
바깥쪽(border box)으로 재면 여백이 큰 행일수록 관대해지고, 같은 화면에서 판정이 갈린다.

    left  = rect.left  + paddingLeft
    right = rect.right - paddingRight
    inner = right - left
    꼬리   = (right - 마지막 자식의 right) / inner
    빈구간 = 자식 사이 가장 큰 틈 / inner        ← 자식이 **정확히 둘**일 때만 본다

### 무엇을 「행」으로 보는가 — 세 조건을 다 넘긴 것만
1. **가로로 자식을 늘어놓는다** — `flex`(column 아님) 또는 `tr`. 세로 스택은 대상이 아니다.
2. **부모 안쪽 폭의 90% 이상**을 차지하고 폭이 400px 이상이다.
3. **그려져 있다** — 배경·테두리·그림자 중 하나가 있거나 `tr` 이다.

세 번째가 핵심이다. 빵부스러기(`.pg-crumb`)와 탭 줄(`.pg-tabs`)은 폭을 다 쓰지만
아무것도 칠하지 않아서 오른쪽이 비어 보이지 않는다. 이 조건을 안 걸면 위반이 112건 나오고
그중 대부분이 "칠하지 않은 상자"다 — 그러면 목록이 쓸모없어진다.

**억지 여백을 자식 둘로 제한한 것도 같은 이유다.** 셋 이상이면 가운데가 벌어져도 그건
열 정렬 문제(§D7)이지 억지 여백이 아니다. 제한을 안 걸면 오른쪽에 액션 하나를 붙인
머리줄이 전부 위반으로 잡힌다.

### 예외는 주석이 아니라 파일이다
`docs/design/density-allow.json` — `key`(경로 + 조상 경로)와 `why`(사유 한 줄)가 짝이다.
사유가 없으면 등록으로 안 친다. 임시 유예는 `until` 에 언제까지인지 적는다.
**검사기는 「더 이상 안 걸리는 허용 항목」도 실패로 낸다** — 남겨 두면 예외였던 것이
영원히 예외로 남고, 목록이 현실과 갈라진다.

허용되는 것은 지금 셋뿐이다.
- **간트 막대** — **막대 안의 빈 곳은 못 채운 폭이 아니라 시간 축 그 자체다. 채우면 기간을
  거짓말한다.** (다음에 누가 "여기 비었네"라고 할 때의 답이다.)
- **오른쪽 끝의 것이 값이 아니라 액션일 때** — 액션은 예측 가능한 자리에 있어야 눌린다.
- **개수를 데이터가 정하는 줄** — 필터 칩이 다섯 개뿐인 화면에는 채울 정보가 없다.

> **배경을 걷어 검사를 피하는 것은 위반이다.** 「그려져 있다」 조건은 자동으로 못 잡는다.
> 카드에서 배경·테두리를 없애는 변경은 리뷰에서 사유를 묻는다.

### §B2 판정식 개정 예약 (§D 착수 시)
「억지 여백」을 **자식 개수**로 판정하는 것은 §B1 문구를 그대로 옮긴 것이고, 그 문구가
실제 기준을 잘못 표현하고 있다. 진짜 기준은 **오른쪽 끝에 놓인 것이 액션이냐 값이냐**다.

    [내 업무] ……… [31건]        값이 멀리 놓였다 — 위반
    [목표]   ……… [전체 관리 →]  액션은 예측 가능한 자리에 있어야 눌린다 — 정상

자식이 둘이든 넷이든 이 구분은 같고, 기계로 잴 수 있다 — 마지막 자식이
`button` · `a` · `[role=button]` · `select` 이거나 그것을 품고 있는가.
**적용 시 확인:** 허용 목록의 「액션이 오른쪽」 3종이 **자동으로 만료되어야 한다.**
만료되지 않으면 판정식이 잘못된 것이다. 만료 규칙이 이 개정의 검증 장치가 된다.

### 검사기가 정적이 아닌 이유
지시서는 "정적 검사기"라고 적었지만, 판정에 필요한 것은 **마지막 자식의 오른쪽 끝 좌표**다.
그건 소스에 없다. 폭은 부모·형제·글자 길이가 같이 정하므로 렌더해야 나온다.
`motion-audit` 은 소스만 봐도 되는 검사라 정적이고, `density-audit` 은 화면에서 잰다.
같은 폴더에 있지만 방식이 다르다 — **검사 방식은 규칙이 정하는 게 아니라 재려는 값이 정한다.**

## 밟히지 않은 분기는 통과가 아니라 미검사다 (§G · MD-P-2026-031 H-2)

`hotfix-walk` 가 기한 표시를 세 등급(지연 · 임박 · 보통)으로 검사한다.
그런데 로컬 데이터에는 **지연만 있고 임박이 한 건도 없었다.** 그대로 돌리면
`12/12 통과` 가 나오고, 임박 분기는 한 번도 안 밟힌 채로 통과한다.

그래서 **없는 등급은 만들어서 재고 되돌린다.**

    const rows = (await pool.query(`SELECT id, due_date FROM task … LIMIT 2`)).rows;
    await pool.query(`UPDATE task SET due_date = CURRENT_DATE + 3 WHERE id = $1`, [rows[0].id]);  // 임박
    await pool.query(`UPDATE task SET due_date = CURRENT_DATE - 5 WHERE id = $1`, [rows[1].id]);  // 지연
    …재고…
    finally { for (const r of touched) await pool.query(`UPDATE task SET due_date = $2 WHERE id = $1`, [r.id, r.due_date]); }

**규칙.**
- 검사는 데이터가 우연히 만들어 준 경우만 밟는다. 등급·상태·경계값 중 현재 데이터에
  없는 것은 **만들어서 재고 되돌린다.**
- 되돌리지 못할 데이터라면 그 검사는 로컬에서만 돌린다.
  쓰기가 있는 검사는 **로컬 DSN 이 아니면 즉시 종료한다** (지시 32). 우회 플래그 금지.
- **모든 분기가 실제로 밟혔음을 보고에 개수로 적는다.** "12/12 통과"는 12개를 다
  밟았다는 뜻이 아니다.

같은 이유로, **올 수 없는 분기는 만들지 않고 그 전제를 단언으로 남긴다.**
홈 「다가오는 일정」은 `lib/home.ts` 가 `due_date >= today` 로 미래만 뽑으므로
지연(D+N)이 올 수 없다. 지연 분기를 만들면 그게 죽은 코드다. 대신
`chk("홈 · 지연은 안 온다", !hLate, …)` 를 둔다. 전제가 깨지면 단언이 먼저 깨진다.

## 삭제는 코드·CSS·검사 세 곳에서 동시에 일어난다 (§G · MD-P-2026-031 H-3)

두 번 같은 일이 났다.

| 지운 것 | 남아서 깨진 검사 |
| --- | --- |
| 목록 행 38px → 44px (§A2) | `subtask-walk` 의 `Math.round(rowH.height) === 38` |
| 연결 모델 1회 안내 `.lmn` (H-3) | `goal-link-walk` 의 `.lmn-x` 클릭 대기 → 타임아웃 |

**규칙.** 화면 요소를 지우는 커밋은 **그것을 찾는 검사도 같은 커밋에서 고친다.**
검사가 먼저 깨지는 것은 사고가 아니라 **설계대로 동작한 것**이다. 그렇게 보고한다.
지운 자리에는 "무엇이 남아야 하는가"를 대신 단언한다 — 지운 것과 애초에 안 그려진 것은
화면에서 똑같이 보이기 때문이다.

    chk("C3-개발과정안내없음", noticeGone === 0 && ulText.includes("연결하면 진척에 집계됩니다"), …)

## 검사기가 낸 숫자도 검사한다 (§G · MD-P-2026-031 §A3)

준비 조사가 세로 정렬 위반 **549건**을 냈다. 고치기 전에 "이 중 몇 건이 진짜인가"를
다시 재는 검사기를 만들었고, 그 검사기가 **549건을 전부 「여러 줄이라 상단 정렬이 맞다」는
예외로 분류**했다. 지시서에 "여러 줄 텍스트 셀은 상단 정렬이 맞다"는 문장이 있었으므로
그대로 넘어갈 수 있었다.

넘어가지 않은 이유는 셀 하나를 열어 봤기 때문이다.

    "연간"  → rects [{top:657,h:15},{top:658,h:13}]   ← 칩 하나가 든 **한 줄**
    줄 수 판정: new Set(rects.map(r => Math.round(r.top))).size  === 2  ← 두 줄로 셌다

한 줄 안에 칩·아이콘처럼 기준선이 1~2px 다른 인라인 요소가 있으면 `top` 이 갈라진다.
줄은 **겹치면 같은 줄**이다. 겹침으로 판정하도록 고치자 예외 549건이 위반 299건이 됐고,
`.prep-t tbody td` 한 줄(`vertical-align: middle`)로 0건이 됐다.

**규칙.**
1. 검사기가 "위반 0건"이나 "전부 예외"를 내면, **그 판정이 맞는지 표본 하나를 눈으로 연다.**
   0건은 통과의 증거이기도 하고 검사기가 눈을 감은 증거이기도 하다. 둘은 화면에서만 갈린다.
2. 판정식을 새로 쓸 때는 **틀렸을 때 어느 쪽으로 틀리는지**를 먼저 적는다.
   위 식은 "위반을 예외로 바꾸는" 쪽으로 틀렸다. 그 방향이 제일 위험하다 — 아무 일도 안 하고
   통과한다.
3. 예외 분류는 **결함을 지우는 버튼**이다. 예외로 빼는 조건은 위반 조건보다 더 좁게 쓴다.
4. **예외가 위반보다 많으면 검사기를 의심한다.** 549 대 0 은 코드가 깨끗하다는 뜻이 아니라
   판정식이 헐겁다는 뜻이다. 예외 비율이 절반을 넘으면 검사기 자체를 먼저 검사한다.

## 규격값은 문서에서 베끼지 말고 화면에서 읽는다 (§G · MD-P-2026-031 §A2)

`subtask-walk` 이 `행 높이 === 38` 을 박아 두고 있었다. §A2 로 행이 44 가 되자
**코드가 아니라 검사가 먼저 깨졌다.** 규격을 옮겨 적은 자리가 두 곳이 되면 한 곳은 반드시 낡는다.

    // 나쁨 — 문서의 숫자를 베낀다
    Math.round(rowH.height) === 38
    // 좋음 — 화면이 실제로 계산한 토큰을 읽는다
    const ROW_H = getComputedStyle(document.documentElement).getPropertyValue("--row-h")

같은 이유로 **폭도 한 곳에서만 정한다.** `table-layout: fixed` 인 표에서 `<col>` 과 CSS 에
폭을 둘 다 적어 두면, CSS 만 고치고 "고쳤는데 안 바뀐다"며 헤맨다. 실제로 그렇게 헤맸다.
표의 폭은 `colgroup` 이 유일한 출처다.

## 부재 단언 규격 — 빈 단언을 막는다 (MD-P-2026-025 §C·§D 회신 지시 28)

"무엇이 **안 나온다**"를 증명하는 검사는 조용히 실패한다.
아무것도 안 나오는 응답은 **차단됐을 때도, 요청이 실패했을 때도 똑같이 생겼기 때문이다.**
그래서 부재 단언에는 아래 세 가지를 반드시 붙인다.

### 28-1 · 상태와 본문 크기를 함께 기록한다
부재 단언을 할 때는 **HTTP 상태와 응답 본문 크기**를 같이 남긴다.
**200 이 아닌 응답에 대한 부재 단언은 무효로 간주한다.**

    ✅  /calendar=200(49,867B) — 제목 없음
    ❌  /api/home=404 — 제목 없음        ← 무효. 404 는 차단이 아니라 요청 실패다

### 28-2 · 짝이 되는 존재 단언을 붙인다
`"팀장에게 안 보인다"` 는 반드시 `"본인에게는 보인다"` 와 **같은 요청 형태로** 함께 확인한다.
한쪽만 있으면 **과다 차단인지 검사 실패인지 구별되지 않는다.**

    팀장  GET /api/notes/7 → 404          (부재)
    본인  GET /api/notes/7 → 200, 제목 포함 (존재)   ← 이 줄이 없으면 위 줄은 증거가 아니다

### 28-3 · 검사 대상 경로가 실제로 있는지 먼저 확인한다
없는 경로를 두드리면 언제나 "안 나온다". 경로 존재를 먼저 확인하고 단언한다.

### 28-4 · 실제로 걸린 사례 두 건

| # | 무슨 일이 있었나 | 어떻게 드러났나 |
| --- | --- | --- |
| 1 | 업무 코멘트 GET 에 가시성 검사가 없어 남의 개인 업무 댓글 본문이 열렸다. 그런데 **검사 코드가 `cmt.status` 를 확인하지 않아** 12/12 통과로 보였다 | 응답을 눈으로 읽다가 `코멘트 200` 을 발견. 단언에 status 를 추가하니 즉시 실패로 바뀌었다 |
| 2 | D-2(팀 캘린더 격리)를 **존재하지 않는 `/api/home`(404)** 에 대고 검사했다. 빈 본문이라 당연히 통과했다 | 상태를 함께 기록하니 404 가 눈에 띄었다. 서버 렌더된 `/calendar` HTML 전문으로 바꿔 다시 쟀다 |

두 사례의 공통점: **검사가 통과했다는 사실 자체는 아무것도 증명하지 않았다.**
통과 개수를 세기 전에 각 단언이 실제로 무엇을 확인했는지 본다.

### 숫자를 보고하려면 실제로 값을 움직여 봐야 한다

> **숫자를 보고하기 위해 실제로 값을 움직여 보는 과정에서 결함이 드러난다.**

실제 사례 (MD-P-2026-024 회신 10 D-5).
"중복 2건을 닫으면 진척이 얼마나 변하나"를 답하려고
목표·업무를 만들어 놓고 실제로 닫아 봤다. 그런데 **기준선이 0% 로 읽혔다.**
원시 INSERT 가 재계산을 안 타서 그런 줄 알고 무해한 PUT 을 넣었는데도 0% 였다.

파고들어 보니 **진행률만 바꾸면 직접 연결(`goal_task`)된 목표가 재계산되지 않았다.**
상태를 건드릴 때까지 옛 숫자가 남아 있었다 —
팀원이 진척을 올려도 목표가 움직이지 않는다는 뜻이다.

    ▶ 진행률 10% → 80%      : 업무 80% · 목표 0%   ← 결함
    ▶ 그 뒤 상태를 변경      : 목표 80%             ← 그제야 반영

코드를 읽는 것으로는 못 찾았다. 재계산 대상 수집 조건이
`statusChanged || goalIds` 였고, 프로젝트 경유 경로(`rollupChanged`)는
이미 `progress` 를 보고 있어서 **읽으면 맞아 보였기 때문이다.**
숫자를 만들어 보고하려는 시도가 아니었으면 드러나지 않았다.

**같은 방식으로 드러난 두 번째 건 (MD-P-2026-027 §H4-②).**
목표 트리 연쇄 모션을 붙이고 나서도 재생되지 않았다. 원인은 모션이 아니라 데이터였다 —
목표 화면이 `TASK_UPDATED` 를 듣지 않아 **업무 진척을 바꿔도 화면을 다시 열기 전까지
숫자가 그대로**였다. 제자리에서 오르는 것을 보여주는 모션인데, 제자리 변화 자체가 없었다.

    ▶ 업무 진행률 0 → 60      : DB 60 · 목표 화면 28% 그대로   ← 결함
    ▶ 화면을 다시 열면         : 목표 화면 28% → 새 값          ← 그제야 반영

024 때와 같다. 코드를 읽어서는 안 걸린다 — 목표 화면은 `GOAL_UPDATED` 를 성실히 듣고 있었고,
그 이벤트만 보면 맞아 보인다. **"값이 오르는 것을 보여주겠다"는 시도**가
"값이 애초에 안 오른다"를 드러냈다.

> 보여주려고 값을 실제로 움직여 보는 과정이 결함을 드러낸다.
> 모션을 붙이는 일이 결함 검사가 되는 이유다.

**규칙.** 보고서에 변화량·집계값을 쓸 때는 그 값을 **실제로 만들어 본다.**
계산식으로 유도한 값을 실측처럼 적지 않는다.

# §H 모션 규격 (MD-P-2026-027 §A) — 승인 전 구현 금지

**이 제품에는 지금 모션이 없다.** 흩어진 효과를 하나씩 넣는 대신 규격을 먼저 세우고
거기서 뽑아 쓴다. 화면마다 다른 시간·다른 곡선을 쓰면 같은 앱으로 안 보인다.

**모션은 상태 변화를 알리는 신호다. 장식으로 쓰지 않는다.**
같은 상태 변화에는 항상 같은 모션을 쓴다.

## H1 토큰

`lib/theme.css` 에 정의한다. **여기 없는 시간·곡선·간격은 쓰지 않는다.**

| 토큰 | 값 | 쓰는 곳 |
| --- | --- | --- |
| `--dur-1` | `120ms` | 색 변화 · hover |
| `--dur-2` | `180ms` | 패널 · 드롭다운 · 토스트 |
| `--dur-3` | `260ms` | 모달 · 목록 재정렬 |
| `--dur-4` | `520ms` | 진척 바 · 숫자 카운트업 — **유일하게 긴 값** |
| `--ease-out` | `cubic-bezier(.2,.8,.2,1)` | 들어오는 것 · 값이 자라는 것 |
| `--ease-in-out` | `cubic-bezier(.4,0,.2,1)` | 자리를 옮기는 것 · 왕복하는 것 |
| `--dur-stroke` | `200ms` | **길이를 그리는 축**(`stroke-dashoffset`) 전용 |
| `--stagger-1` | `20ms` | 같은 층의 요소가 **동시에** 들어올 때의 간격 |
| `--stagger-2` | `60ms` | 층을 타고 올라가는 **순서**를 보여줄 때의 간격 |

`--dur-stroke` 는 `--dur-*` 와 **다른 계열**이다. 시간이 아니라 획이 끝까지 보이는 데
필요한 길이라서 `--dur-2`(180)보다 조금 길다. 그래도 **토큰으로 등재한다** —
예외를 문서에만 적어 두면 "§H 에 없는 값은 쓰지 않는다"가 스스로 깨지고,
다음 사람이 "이것도 예외"라며 숫자를 하나 더 넣는다 (§A 회신 [확정]).

## H2 규칙

| | 규칙 |
| --- | --- |
| 허용 속성 | `transform` · `opacity` · `background-color` · `border-color` · `box-shadow` · `stroke-dashoffset` **뿐** |
| 금지 속성 | `width` · `height` · `top` · `left` · `margin` · `padding` — 레이아웃을 다시 계산시킨다 |
| 진척 바 | `width` 가 아니라 **`transform: scaleX()`**, `transform-origin: left` |
| 이동 거리 | **8px 이내** |
| 스케일 | **0.96 ~ 1.0** |
| 동시 개수 | 한 번에 움직이는 요소 **최대 3개** |
| stagger | **`--stagger-1`**, **최대 6개**까지 |
| 무한 반복 | **스켈레톤 shimmer 하나뿐.** 스피너는 계속 금지 |

### 접근성 — `prefers-reduced-motion: reduce`

```css
@media (prefers-reduced-motion: reduce) {
  /* transform 애니메이션을 뺀다. opacity 만 남긴다. */
  /* 모든 duration 을 --dur-1 로 줄인다. */
}
```

없애는 것이 아니라 **줄이는 것**이다. 상태 변화를 알리는 신호는 남겨야 한다.

### shimmer 는 §A-4 를 뒤집는 것이 아니다

MD-P-2026-026 §A-4 는 "shimmer 금지 — 움직임은 후속 모션 규격에서"였다.
그 후속이 이 문서이고, **스켈레톤 한 곳에만** 허용한다.
`1.2s linear infinite`, `background-position` 만 움직인다.
`reduce` 에서는 정지하고 `--surface-2` 단색으로 남는다 — 지금 동작 그대로다.

## H3 기능적 모션 — 전부 구현 대상

| 상태 변화 | 모션 | 시간 |
| --- | --- | --- |
| 진척 바 값 변경 | `scaleX` 0→값, `origin: left` | `--dur-4` |
| 진척 숫자 변경 | `tabular-nums` 카운트업 | `--dur-4` |
| 업무 완료 체크 | 체크마크 `stroke-dashoffset` 그리기 | `--dur-stroke` |
| 〃 (같은 동작) | 행 텍스트 `opacity` 1→.55 | `--dur-1` |
| 목록 필터·정렬 변경 | FLIP — `transform` 으로 이동 | `--dur-3` |
| 행 제거 | `opacity` + `translateY(-4px)` | `--dur-2` |
| 값이 바뀐 칸 | 배경 하이라이트 **400ms 유지 후 400ms 페이드** | — |
| 패널 열림 | `translateX` + 스크림 페이드 | `--dur-2` |
| 모달 열림 | `scale` .96→1 + `opacity` | `--dur-3` |
| 모달 닫힘 | 역방향 | `--dur-2` |
| 탭 전환 | 활성 밑줄이 미끄러짐 | `--dur-2` |
| 카드 hover | `--e1` → `--e2` | `--dur-1` |
| 저장됨 표시 | `opacity` + `translateY` 4px, **2초 뒤 페이드** | `--dur-2` |
| 로딩 | 스켈레톤 shimmer | `1.2s linear infinite` (무한 반복 유일) |

표의 모든 값은 H1 토큰 참조다. **하드코딩된 숫자는 없다.**

## H4 시그니처 2곳 — 여기만 공을 들인다

### ① 홈 다크 히어로 타임라인

진입 시 각 바가 왼쪽에서 자라난다 — `scaleX`, `origin: left`, stagger **`--stagger-1`**, **최대 6개**.

**세션당 1회만 재생한다.** 매번 재생하면 홈에 갈 때마다 기다려야 하고, 그건 방해다.
`sessionStorage` 로 판정한다(계정이 아니라 세션 — 탭을 새로 열면 한 번 더 봐도 괜찮다).

### ② 목표 트리 — 이 제품의 서사

업무 진척이 바뀌면 그 값이 **월 → 분기 → 연간** 목표로 차례로 카운트업된다.
stagger **`--stagger-2`**, 각 단계 `--dur-4`. 올라가는 동안 해당 행의 진척 바도 같이 찬다.

> **"내가 한 일이 위로 올라간다"를 눈으로 보여주는 것이 이 제품의 핵심이다.**

**사용자가 직접 값을 바꿨을 때만 재생한다.** 화면 재진입·폴링 갱신에서는 재생하지 않는다.
남이 바꾼 값이 내 화면에서 혼자 굴러가면 무슨 일이 일어났는지 알 수 없다.

여기가 `--stagger-2` 를 쓰는 유일한 자리다. `--stagger-1`(20ms)은 **같은 층의 여러 요소**가
동시에 들어올 때의 간격이고, `--stagger-2`(60ms)는 **층을 타고 올라가는 순서**를 보여주는
간격이다. 순서가 보여야 하므로 더 길다.

## H5 하지 않는 것

표현적 모션은 넣지 않는다 — 페이지 진입 stagger 등장 · 카드 부유 · 패럴랙스 ·
바운스 · 스프링 오버슈트. **§H 표에 없는 모션은 금지다.**
