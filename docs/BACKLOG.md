## B-1 — 월간 보고의 상시 업무 건수 표기

**배경.** MD-P-2026-024 §3 에서 진척 집계 대상에서 `work_type='routine'`(상시 업무)을 제외하기로 확정했다.
상시 업무는 완료 개념이 없어 분모에 넣으면 진척을 왜곡하기 때문이다.

**문제.** 집계에서 빠지면서 월간 성과 보고에서 상시 업무가 **통째로 보이지 않게** 된다.
실제로 수행한 일이 보고서에서 사라지는 것은 정직하지 않다.

**할 일.** 월간 보고에 진척과 **별도 항목**으로 건수만 표기한다.

- 표기 예: `상시 업무 7건 수행`
- 진척률·달성률 계산에는 **넣지 않는다.** 어디까지나 별도 표기다.
- 대상: `work_type='routine'` 이면서 해당 월에 활동이 있었던 업무.
  "활동"의 정의(완료 건수인지, 갱신 건수인지)는 착수 시 확정할 것.

**손댈 곳(예상).** `lib/perf-report.ts` · `components/PerfReport.tsx`.
진척 계산기(`lib/progress.ts`)는 건드리지 않는다 — 집계 제외 규칙은 그대로 둔다.

## B-2 — 업무 저장 직전 제목 유사 안내

**확정 문장 (MD-P-2026-024 회신 8).**

> 업무 저장 직전, 같은 영역·같은 분기 안에서 정규화 제목이 완전 일치하면
> 기존 업무를 링크로 안내한다. 저장은 막지 않는다. pg_trgm 미사용.

**배경.** 업무를 만드는 경로 3개(`POST /api/tasks` · `POST /api/signals/[id]` ·
시드 스크립트) 중 어디에도 중복 검사가 없고, `task` 테이블에 unique 제약도 0건이다.
같은 제목을 몇 번이든 넣을 수 있고 아무 경고도 뜨지 않는다.

**유니크 제약을 걸지 않는 이유.**
"카메라 캘리브레이션"처럼 **정당하게 반복되는 업무**가 실제로 있다.
제약을 걸면 그 반복을 못 만든다. 중복인지 아닌지는 제목만으로 판정할 수 없고,
판단은 사람이 해야 한다. 그래서 **저장을 막는 대신 알려주기만 한다.**

**유사도를 단순하게 두는 이유.**
`pg_trgm` 확장 설치는 프로덕션 DB 권한이 필요해 피한다.
공백·괄호·`(1)` 같은 꼬리표를 떼고 정규화한 제목의 **완전 일치**만 봐도
지금까지 관측된 중복 유형은 대부분 잡힌다. 못 잡는 것은 사람이 본다.

**범위.** 일반 생성 경로뿐 아니라 **신호 → 업무 전환 경로에도** 넣는다.
(전환 자체의 중복은 회신 8 지시 26 에서 이미 차단했다. B-2 는 *제목이 비슷한
다른 업무*를 알려주는 별개 장치다.)

**착수 전 확인.** "같은 분기"의 기준을 `due_date` 로 볼지 `created_at` 으로 볼지
정할 것. 기한 없는 업무가 많아 `created_at` 이 현실적이다.

## B-3 — /huddle §G 규격 정리 (허들룸 재설계 때 함께)

**확정 (MD-P-2026-024 회신 9).**

> 허들룸은 후속 지시에서 "회의 1건 = 세션 1개" 구조로 재설계 예정이라
> 지금 규격을 입히면 그대로 폐기됩니다.
> 붕괴가 아니라 규격 위반 수준이므로 그때 함께 처리합니다.

**실측 (2026-08-06, `scripts/measure-screens.mjs`).**

| 경로 | 상태 | scrollHeight | §G 폰트 위반 | §G 라운드 위반 |
| --- | --- | --- | --- | --- |
| /huddle | 200 | 1252px | 32 | 12 |

레이아웃 붕괴는 없다. `div.top` 1152×40 · `div.head` 1104×78 · `section` 1104×205 로
크기가 정상이다 — 고쳐야 할 것은 **폰트 스케일과 라운드 값**뿐이다.

**지금 손대지 않는 이유.** 재설계가 이 화면의 마크업을 갈아엎는다.
지금 §G 를 입히면 그 CSS 가 통째로 버려진다. 두 번 일하지 않는다.

**착수 조건.** 허들룸 "회의 1건 = 세션 1개" 재설계 지시가 내려온 뒤,
그 작업의 일부로 처리한다. 단독으로 먼저 하지 않는다.

## B-4 — 목표에 생성자 기록이 없다

**확정 (MD-P-2026-024 회신 9).**

> `goal` 테이블에 `created_by` 가 없고 `owner_actor_id` 만 있다.
> 팀 목표는 소유자가 비어 있는 것이 정상이라, 누가 언제 만들었는지 추적할 방법이 없다.
> 업무·논의에는 생성자가 있는데 목표에만 없다.

**발견 경위.** 지시 25(중복 조사 SQL) 작성 중.
"목표 #13·#14·#15·#17 의 생성자"를 뽑으려다 컬럼이 없다는 것을 확인했다.
`owner_actor_id` 로 대체했으나, 팀 목표(`scope='team'`)는 소유자가 NULL 이라
**결국 생성자를 알 수 없다.**

**왜 문제인가.** 같은 제목의 목표가 여러 건 있을 때
"자동 생성인가 사람이 만든 것인가"를 판정할 근거가 `created_at` 하나뿐이다.
생성자가 있으면 한 번에 끝날 판단이다.

**할 일(예상).**
- `goal.created_by INTEGER REFERENCES actor(id)` 추가.
- **기존 행 backfill 금지.** 모르는 것을 추정해 채우지 않는다 (MD-P-2026-024 §2 원칙).
  기존 목표는 `NULL` 로 두고 "기록 없음"으로 표시한다.
- `POST /api/goals` 에서 세션 사용자로 채운다.

**착수 시점.** MD-P-2026-025 이후. 이번 지시로 구현하지 않는다.

## B-5 — 타임라인 경로의 private 업무 노출 실측 (판정 보류)

**확정 (MD-P-2026-025 §A·§B 회신).**

> Notion 토큰 없이 500 이 난 것을 통과로 세지 않은 판단이 맞습니다.
> 다만 구조적 근거는 남겨두세요.

**현재 상태 — 판정 보류.**
`§A3` 의 열 경로 중 ⑤ 타임라인만 **실측하지 못했다.**
로컬에 `NOTION_TOKEN` 이 없어 `/api/notion/timeline` 이 500 을 돌려준다.
500 은 "차단됐다"가 아니라 **이 경로를 행사하지 못했다**는 뜻이므로 통과로 세지 않는다.

**구조적 근거 (실측이 아님).**

| 확인 | 결과 |
| --- | --- |
| `app/api/notion/timeline/route.ts` 전문 | `queryTimeline()` 한 줄만 호출. task 조회 없음 |
| `lib/notion.ts` 안의 `FROM task` / `JOIN task` | **0건** |
| `lib/notion.ts` 의 DB 접근 전부 | `SELECT value FROM config WHERE key='notion_scope'` **1곳뿐** |
| 데이터 출처 | `notionFetch('/data_sources/{dsId}/query')` — 외부 Notion API |
| `components/TimelineView.tsx` 의 fetch | `/api/notion/timeline` 하나뿐 |

즉 이 화면의 데이터는 **우리 DB 가 아니라 Notion 에서 온다.**
`task.visibility` 가 관여할 여지가 구조적으로 없다.
다만 Notion 쪽에 업무를 밀어 넣는 경로(`createTimelinePage` 등)가 개인 업무를
올려보내면 그때는 Notion 에서 샌다 — **그 방향이 진짜 확인 대상이다.**

**할 일.**
1. Notion 연결 환경에서 `/api/notion/timeline` 을 실제로 호출해 private 업무 노출 여부 실측.
2. 반대 방향 점검 — 개인 업무가 Notion 타임라인으로 **밀려 올라가지 않는지** 확인.
   (현재 승인 경로 `POST /api/drafts/{id}/approve` 만 Notion 에 쓴다)
3. 결과를 §A3 표에 채워 넣고 이 항목을 닫는다.

## B-6 — 개인 메모에 이미지 블록 (blob 스코프 부재)

**발견 경위.** MD-P-2026-025 §C 구현 중.
메모는 문서형 업무의 편집기(`DocEditor`)를 그대로 재사용하는데,
이미지 블록만 동작하지 않는다.

**원인.** `lib/blob.ts` 의 `BlobScopeKind` 가
`"project" | "task" | "review" | "signal"` 네 가지뿐이고 `note` 가 없다.
경로를 만들 수도, `canReadBlob`/`canWriteBlob` 으로 접근을 판정할 수도 없다.

**이번 단계에서 넣지 않은 이유.**
스코프를 추가하려면 `lib/blob-access.ts` 에 **새 접근 판정 분기**가 생긴다.
§A3 는 누출 경로를 하나하나 실제 요청으로 확인하라고 정했는데,
검증하지 못한 접근 경로를 늘리는 것은 그 취지와 정면으로 어긋난다.
지금은 `blobReady: false` 로 내려보내 편집기가 이미지 명령 자체를 막는다 —
별도 차단 장치를 만들지 않고 기존 규칙을 그대로 썼다.

**할 일.**
1. `BlobScopeKind` 에 `note` 추가 + `PATH_RE` 확장.
2. `canReadBlob`/`canWriteBlob` 에 `note` 분기 — 판정은 `owner_actor_id = viewer` 하나뿐이다.
3. `app/api/notes/[id]` 가 `blobReady: blobEnabled()` 를 내려보내게 변경.
4. **§A3 형식으로 실측** — 남의 메모 이미지 pathname 을 직접 호출해 차단되는지 확인.
