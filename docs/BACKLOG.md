## B-1 — 월간 보고의 상시 업무 건수 표기

**배경.** MD-P-2026-024 §3 에서 진척 집계 대상에서 `work_type='routine'`(상시 업무)을 제외하기로 확정했다.
상시 업무는 완료 개념이 없어 분모에 넣으면 진척을 왜곡하기 때문이다.

**문제.** 집계에서 빠지면서 월간 성과 보고에서 상시 업무가 **통째로 보이지 않게** 된다.
실제로 수행한 일이 보고서에서 사라지는 것은 정직하지 않다.

**할 일.** 월간 보고에 진척과 **별도 항목**으로 건수만 표기한다.

- 표기 예: `상시 업무 7건 수행`
- 진척률·달성률 계산에는 **넣지 않는다.** 어디까지나 별도 표기다.
- 대상: `work_type='routine'` 이면서 해당 월에 활동이 있었던 업무.
  "활동"의 정의(완료 건수인지, 갱신 건수인지)는 착수 시 확정할 것.

**손댈 곳(예상).** `lib/perf-report.ts` · `components/PerfReport.tsx`.
진척 계산기(`lib/progress.ts`)는 건드리지 않는다 — 집계 제외 규칙은 그대로 둔다.

## B-2 — 업무 저장 직전 제목 유사 안내

**확정 문장 (MD-P-2026-024 회신 8).**

> 업무 저장 직전, 같은 영역·같은 분기 안에서 정규화 제목이 완전 일치하면
> 기존 업무를 링크로 안내한다. 저장은 막지 않는다. pg_trgm 미사용.

**배경.** 업무를 만드는 경로 3개(`POST /api/tasks` · `POST /api/signals/[id]` ·
시드 스크립트) 중 어디에도 중복 검사가 없고, `task` 테이블에 unique 제약도 0건이다.
같은 제목을 몇 번이든 넣을 수 있고 아무 경고도 뜨지 않는다.

**유니크 제약을 걸지 않는 이유.**
"카메라 캘리브레이션"처럼 **정당하게 반복되는 업무**가 실제로 있다.
제약을 걸면 그 반복을 못 만든다. 중복인지 아닌지는 제목만으로 판정할 수 없고,
판단은 사람이 해야 한다. 그래서 **저장을 막는 대신 알려주기만 한다.**

**유사도를 단순하게 두는 이유.**
`pg_trgm` 확장 설치는 프로덕션 DB 권한이 필요해 피한다.
공백·괄호·`(1)` 같은 꼬리표를 떼고 정규화한 제목의 **완전 일치**만 봐도
지금까지 관측된 중복 유형은 대부분 잡힌다. 못 잡는 것은 사람이 본다.

**범위.** 일반 생성 경로뿐 아니라 **신호 → 업무 전환 경로에도** 넣는다.
(전환 자체의 중복은 회신 8 지시 26 에서 이미 차단했다. B-2 는 *제목이 비슷한
다른 업무*를 알려주는 별개 장치다.)

**착수 전 확인.** "같은 분기"의 기준을 `due_date` 로 볼지 `created_at` 으로 볼지
정할 것. 기한 없는 업무가 많아 `created_at` 이 현실적이다.

### 진짜 원인은 앱이 아니었다 (MD-P-2026-024 회신 10 판정 B)

> **앱의 생성 경로보다 초기 일괄 등록에서 중복이 들어오는 경로가 실제 원인이었다.
> 향후 외부 데이터를 일괄 등록할 때는 등록 전에 정규화 제목 중복 리포트를 먼저 낸다.**

근거: 중복 업무 #32·#38·#17·#26 의 `created_at` 이 `2026-07-27 05:43:41.389018+00` 로
**소수점까지 완전히 동일**했다. 앱의 생성 경로가 아니라 데이터 이관 시점에
원본의 중복이 그대로 들어온 것이다. (#42 만 같은 날 09:10:03 에 앱에서 따로 만들어졌다)

그래서 B-2(저장 직전 안내)는 **두 번째 방어선**이다.
첫 번째 방어선은 **일괄 등록 전 중복 리포트**이고, 이쪽이 더 중요하다.

## B-3 — /huddle §G 규격 정리 (허들룸 재설계 때 함께)

**확정 (MD-P-2026-024 회신 9).**

> 허들룸은 후속 지시에서 "회의 1건 = 세션 1개" 구조로 재설계 예정이라
> 지금 규격을 입히면 그대로 폐기됩니다.
> 붕괴가 아니라 규격 위반 수준이므로 그때 함께 처리합니다.

**실측 (2026-08-06, `scripts/measure-screens.mjs`).**

| 경로 | 상태 | scrollHeight | §G 폰트 위반 | §G 라운드 위반 |
| --- | --- | --- | --- | --- |
| /huddle | 200 | 1252px | 32 | 12 |

레이아웃 붕괴는 없다. `div.top` 1152×40 · `div.head` 1104×78 · `section` 1104×205 로
크기가 정상이다 — 고쳐야 할 것은 **폰트 스케일과 라운드 값**뿐이다.

**지금 손대지 않는 이유.** 재설계가 이 화면의 마크업을 갈아엎는다.
지금 §G 를 입히면 그 CSS 가 통째로 버려진다. 두 번 일하지 않는다.

**착수 조건.** 허들룸 "회의 1건 = 세션 1개" 재설계 지시가 내려온 뒤,
그 작업의 일부로 처리한다. 단독으로 먼저 하지 않는다.

## B-4 — 목표에 생성자 기록이 없다

**확정 (MD-P-2026-024 회신 9).**

> `goal` 테이블에 `created_by` 가 없고 `owner_actor_id` 만 있다.
> 팀 목표는 소유자가 비어 있는 것이 정상이라, 누가 언제 만들었는지 추적할 방법이 없다.
> 업무·논의에는 생성자가 있는데 목표에만 없다.

**발견 경위.** 지시 25(중복 조사 SQL) 작성 중.
"목표 #13·#14·#15·#17 의 생성자"를 뽑으려다 컬럼이 없다는 것을 확인했다.
`owner_actor_id` 로 대체했으나, 팀 목표(`scope='team'`)는 소유자가 NULL 이라
**결국 생성자를 알 수 없다.**

**왜 문제인가.** 같은 제목의 목표가 여러 건 있을 때
"자동 생성인가 사람이 만든 것인가"를 판정할 근거가 `created_at` 하나뿐이다.
생성자가 있으면 한 번에 끝날 판단이다.

**할 일(예상).**
- `goal.created_by INTEGER REFERENCES actor(id)` 추가.
- **기존 행 backfill 금지.** 모르는 것을 추정해 채우지 않는다 (MD-P-2026-024 §2 원칙).
  기존 목표는 `NULL` 로 두고 "기록 없음"으로 표시한다.
- `POST /api/goals` 에서 세션 사용자로 채운다.

**착수 시점.** MD-P-2026-025 이후. 이번 지시로 구현하지 않는다.

## B-5 — 타임라인 경로의 private 업무 노출 실측 (판정 보류)

**확정 (MD-P-2026-025 §A·§B 회신).**

> Notion 토큰 없이 500 이 난 것을 통과로 세지 않은 판단이 맞습니다.
> 다만 구조적 근거는 남겨두세요.

**현재 상태 — 판정 보류.**
`§A3` 의 열 경로 중 ⑤ 타임라인만 **실측하지 못했다.**
로컬에 `NOTION_TOKEN` 이 없어 `/api/notion/timeline` 이 500 을 돌려준다.
500 은 "차단됐다"가 아니라 **이 경로를 행사하지 못했다**는 뜻이므로 통과로 세지 않는다.

**구조적 근거 (실측이 아님).**

| 확인 | 결과 |
| --- | --- |
| `app/api/notion/timeline/route.ts` 전문 | `queryTimeline()` 한 줄만 호출. task 조회 없음 |
| `lib/notion.ts` 안의 `FROM task` / `JOIN task` | **0건** |
| `lib/notion.ts` 의 DB 접근 전부 | `SELECT value FROM config WHERE key='notion_scope'` **1곳뿐** |
| 데이터 출처 | `notionFetch('/data_sources/{dsId}/query')` — 외부 Notion API |
| `components/TimelineView.tsx` 의 fetch | `/api/notion/timeline` 하나뿐 |

즉 이 화면의 데이터는 **우리 DB 가 아니라 Notion 에서 온다.**
`task.visibility` 가 관여할 여지가 구조적으로 없다.
다만 Notion 쪽에 업무를 밀어 넣는 경로(`createTimelinePage` 등)가 개인 업무를
올려보내면 그때는 Notion 에서 샌다 — **그 방향이 진짜 확인 대상이다.**

**할 일.**
1. Notion 연결 환경에서 `/api/notion/timeline` 을 실제로 호출해 private 업무 노출 여부 실측.
2. 반대 방향 점검 — 개인 업무가 Notion 타임라인으로 **밀려 올라가지 않는지** 확인.
   (현재 승인 경로 `POST /api/drafts/{id}/approve` 만 Notion 에 쓴다)
3. 결과를 §A3 표에 채워 넣고 이 항목을 닫는다.

## B-6 — 개인 메모에 이미지 블록 (blob 스코프 부재)

**발견 경위.** MD-P-2026-025 §C 구현 중.
메모는 문서형 업무의 편집기(`DocEditor`)를 그대로 재사용하는데,
이미지 블록만 동작하지 않는다.

**원인.** `lib/blob.ts` 의 `BlobScopeKind` 가
`"project" | "task" | "review" | "signal"` 네 가지뿐이고 `note` 가 없다.
경로를 만들 수도, `canReadBlob`/`canWriteBlob` 으로 접근을 판정할 수도 없다.

**이번 단계에서 넣지 않은 이유.**
스코프를 추가하려면 `lib/blob-access.ts` 에 **새 접근 판정 분기**가 생긴다.
§A3 는 누출 경로를 하나하나 실제 요청으로 확인하라고 정했는데,
검증하지 못한 접근 경로를 늘리는 것은 그 취지와 정면으로 어긋난다.
지금은 `blobReady: false` 로 내려보내 편집기가 이미지 명령 자체를 막는다 —
별도 차단 장치를 만들지 않고 기존 규칙을 그대로 썼다.

**할 일.**
1. `BlobScopeKind` 에 `note` 추가 + `PATH_RE` 확장.
2. `canReadBlob`/`canWriteBlob` 에 `note` 분기 — 판정은 `owner_actor_id = viewer` 하나뿐이다.
3. `app/api/notes/[id]` 가 `blobReady: blobEnabled()` 를 내려보내게 변경.
4. **§A3 형식으로 실측** — 남의 메모 이미지 pathname 을 직접 호출해 차단되는지 확인.

## B-7 — EmptyState 를 쓰지 않는 빈 상태 50곳

**발견 경위.** 지시 29(빈 상태 전수 점검) 수행 중.
`EmptyState` 컴포넌트를 쓰는 곳은 **9곳뿐**이고, 나머지 **50곳**은
`.gempty` · `.dl-empty` · `.rp-empty` · `.ho-empty` 같은 자체 마크업으로
"…이 없습니다" 한 줄만 띄운다. 즉 §G 의 3요소 규격이 **적용 대상 밖**이다.

예:

    components/GoalsView.tsx:176   <div className="dl-empty"><p>팀 목표가 없어요</p>…
    components/AreaView.tsx:133    <p className="gempty">이 영역에 프로젝트가 없습니다.</p>
    components/PerfReport.tsx:26   function Empty({ text = "이번 달 해당 항목이 없습니다." })
    components/ReportView.tsx:64   <p className="rp-empty">해당 월 목표가 없습니다.</p>

**부작용 하나가 이미 확인됐다.** `/goals` 가 목표 0건일 때 `GoalsView` 의
`.dl-empty` 가 먼저 걸려서, `GoalTree` 안에 있는 `EmptyState` 는 **실제로는 도달하지 않는다.**
지시 29-2 점검에서 이 경로에 끝내 도달하지 못한 이유가 이것이다.

**판단이 필요한 지점.** 50곳을 전부 `EmptyState` 로 바꾸는 것이 맞는지는 확실치 않다.
섹션 안의 한 줄짜리 빈 표시(예: 월간 보고의 항목별 "없습니다")까지 96px 아이콘을 넣으면
보고서가 아이콘 밭이 된다. **화면 전체가 비는 곳**과 **섹션 한 칸이 비는 곳**을
다른 규격으로 나누는 편이 맞아 보인다.

**할 일(제안).**
1. 50곳을 "화면 전체" / "섹션 한 칸"으로 분류.
2. 화면 전체 → `EmptyState` 3요소로 이관.
3. 섹션 한 칸 → 아이콘 없는 1줄 규격을 §G 에 **정식으로 정의**한다.
   지금은 규격이 없어서 그냥 방치된 것이지, 의도적으로 뺀 것이 아니다.
4. 이관 후 지시 29-2 방식(실제로 띄워 DOM 에서 3요소 확인)으로 재점검.

**이번 지시로 하지 않았다.** 지시 29 는 `EmptyState` 사용처를 대상으로 했고,
50곳 이관은 범위가 다르며 규격 결정이 먼저 필요하다.

### 종결 — MD-P-2026-026 §A 에서 처리 (2026-08-07) · **닫음**

2단 규격(전체 `EmptyState` / 섹션 `SectionEmpty`)을 §G 에 정의하고 전수 이관했다.
로딩(`Skeleton`)·오류(`ErrorNote`) 규격도 함께 정의했다. **B-7 닫음.**

## B-8 — 폼 제출 오류는 아직 `.gerr` 한 줄이다

**발견 경위.** MD-P-2026-026 §A 이관 중.

§A-5 오류 규격(`ErrorNote`)은 **데이터를 못 불러온 상태**를 대상으로 정의했고,
그 자리는 전부 이관했다. 그런데 **폼 제출 실패**는 성격이 다르다 —
"계정 발급 실패" · "저장 실패" 같은 것들로, 아직 `.gerr` 한 줄로 남아 있다.

    components/GoalTree.tsx:81 · 135 · 290     목표 추가 폼
    components/ProjectsIndexView.tsx:68        새 프로젝트 폼
    components/HuddleFeed.tsx:90               허들 전송
    components/ProfileView.tsx:127 · 163       프로필 · 비밀번호
    components/PasswordGate.tsx:51             로그인
    components/MemberManager.tsx (일부)         계정 발급

**판단이 필요한 지점.** 제출 실패에 "다시 시도" 버튼을 붙이는 것이 맞는지 모르겠다.
누르면 같은 값으로 또 실패한다. 폼 오류는 **입력 옆에 붙는 것**이 맞고,
그렇다면 §A-5 와 다른 규격이어야 한다. 규격 결정이 먼저다.

**이번에 하지 않았다.** §A 범위는 "빈 상태 · 로딩 · 오류(불러오기)" 였다.

## B-10 — 로그인 전 경로로 되돌리기 (returnTo)

## B-11 — 영역 화면(AreaView)이 도달 불가가 됐다

## B-12 — 「팀 › 업무」 링크의 assignee 빈 값

**발견 경위.** MD-P-2026-027 §B1 사이드바 재구성.

「내 업무」와 「업무」는 같은 화면의 다른 조건이다.
전자는 담당=본인, 후자는 담당 무관이라 `href="/tasks?assignee="` 로 **빈 값**을 넘긴다.

지금은 동작한다(빈 문자열이 "전체 담당"으로 해석됨). 다만 URL 이 지저분하고,
나중에 `assignee` 를 필수로 바꾸면 조용히 깨진다.
`?assignee=all` 같은 명시값으로 바꾸는 편이 안전하다 — 별건으로 등록한다.

## B-13 — `goal_source` 의 `inherited` 를 `unset` 으로 이름 정리

> 지시서에는 "B-11 로 등록"이라 적혀 있었으나 B-11·B-12 가 이미 쓰이고 있어
> **B-13 으로 붙였습니다.** 내용은 지시하신 그대로입니다.

**발견 경위.** MD-P-2026-030 §A4 — 목표 상속을 없앴다.

`task.goal_source` 는 세 값을 갖는다. 상속이 사라진 지금 뜻은 이렇다.

    none       사용자가 "목표 없음"을 명시적으로 골랐다. 미연결 배너에 오르지 않는다.
    manual     보통 상태. 새 업무는 전부 이 값으로 만들어진다.
    inherited  **역사적 값이다.** 상속이 있던 시절 "프로젝트를 따라간다"는 뜻이었고,
               지금은 '미지정'을 뜻한다. 새로 만들어지지 않는다.

`inherited` 라는 이름이 없어진 개념을 가리키고 있어, 읽는 사람이
"아직 상속이 도는구나"로 오해할 수 있다. `unset` 이 맞는 이름이다.

**지금 하지 않은 이유.** 값 이름을 바꾸려면 마이그레이션(UPDATE + CHECK 교체)이 필요하고,
[확정] 지시가 **"inherited 19건은 값을 유지한다. CHECK 를 좁히지 마세요"** 였다.
새 업무가 이 값을 갖지 않게 막는 것까지가 030 의 범위다.

**할 일(제안).**
1. `UPDATE task SET goal_source = 'unset' WHERE goal_source = 'inherited'`
2. CHECK 를 `('unset','manual','none')` 로 교체 — 롤백은 역방향 UPDATE + 원래 CHECK.
3. `lib/goal-inherit.ts` 를 `lib/goal-source.ts` 로 옮긴다. **파일 이름도 같이 낡았다.**
4. 코드에서 `"inherited"` 문자열을 훑는다 (지금은 타입 정의와 주석에만 남아 있다).
5. 검증: 이름 변경 후 미연결 배너 건수가 **바뀌지 않아야 한다** — 뜻이 같은 값의 개명이므로.

## B-14 — 410 라우트 정리 (팀 오픈 후 한 달 뒤)

**확정 (MD-P-2026-030 §A·§B 회신 [승인] ⑦).**

> app/api/goals/[id]/projects/route.ts — 삭제하지 말고 410 그대로 두세요.
> 열려 있던 탭이나 캐시된 클라이언트가 호출하면 500 이 아니라 410 을 받아야 합니다.

**지금 상태.** GET·POST·DELETE 전부 410 을 돌려준다.
본문은 사람이 읽을 사유 한 줄이다 —
"목표-프로젝트 연결은 더 이상 지원하지 않습니다. 업무를 목표에 직접 연결하세요."
왜 없어졌는지도 파일 안에 적어 뒀다. 다음 사람이 다시 만들지 않게 하기 위해서다.

**같은 배포에서 지운 것.** 이 라우트를 부르던 화면 둘은 삭제했다(승인 완료).

    components/GoalProjectPicker.tsx
    components/GoalLinkBanner.tsx

**할 일.** 팀 오픈 후 **한 달**이 지나면 라우트 파일도 지운다.
그때는 이 경로를 기억하는 열린 탭이나 캐시가 남아 있지 않다.

**착수 전 확인.** 지우기 전에 액세스 로그에서 이 경로 호출이 0건인지 본다.
0건이 아니면 어디서 부르는지부터 찾는다 — 남아 있다는 뜻이다.
